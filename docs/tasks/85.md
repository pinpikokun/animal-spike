# 5. #85 CPUのジャンプ発火条件を原作のAND判定へ絞る

**中身**: 原作は「頂点付近 AND 横に流れていない AND 十分高い」のANDで跳ぶ球を選び、
悪い球には跳ばない。現行は「会合できるか」だけを見ており、悪い球でも跳ぶ。

**根拠**: 実測。原作資料の5節（0x8824）の条件（横20px以内、|ball_vx|<5、
|ball_vy|<しきい値10、ball_y<200、かつアタッカー役のみ）を自分で読んでいる。

**なぜP2の4位か**: #82 と同じ「打つ前に弾く」系。まとめてやると効率が良い。
単独でも「変な球に跳んで自滅する」を減らせる。

## 設計前調査（2026-07-29）

**状態: 数値契約の矛盾により、実装前で停止。** 原作のAND構造は確定しているが、
この文書の数値を現行単位へ移す方法が承認済み資料と一致していない。

- 横距離 `0x14` は原作の内部20目盛りである。承認済み換算
  `docs/superpowers/specs/2026-07-25-cpu-positioning-redesign.md` 4A.1では
  x方向を4倍するため、本作では80pxになる。この文書の「20px」と矛盾する。
- `docs/reference/original-vb22-physics.md` 1・2節では、原作の速度は座標へ毎フレーム加える
  値で、xは1目盛り約4px、yは1目盛り約1ラインである。既存の約30fps仮定から
  本作の60tick/sへ時間換算する候補値は、`|ball_vx| < 10px/tick`、
  `|ball_vy| < 5px/tick` となる。これは実機fps未確認のため確定値ではない。
- 原作コードの `ball_update()` は `0x0E6A` を毎回減らし、0の回だけ本体を更新して
  `0x0E6C` を再装填する。通常値2は外側ループ2周に1回、高速状態の値1は毎周更新を
  意味する。ただし通常試合ループにはタイマ待ち・垂直同期待ちがなく、入力読取中の
  固定CPUサイクル遅延しか確認できない。したがって毎秒の更新回数と約30fps仮定は
  静的解析では確定せず、上記10px/tick・5px/tickは時間換算を採る設計判断である。
- 本作の通常トス初速は上向き約-7.8px/tickである。縦条件を換算せず
  `|ball_vy| < 10px/tick` とすると、投げた直後から通って頂点付近という効果が成立しない、
  という導出になる。
- 承認済み換算はyを1目盛り約1ラインとする。原作の床288と `ball_y < 200` は
  床から88ライン以上を意味する。本作の床320で高さを保存するなら `ball_y < 232`、
  絶対値を保存するなら `ball_y < 200` となり、判断が要る。
- 承認済み役割設計はアタッカーを禁止でなく優先権とし、役持ちが会合不能なら相方の代行を
  許可している。この文書の「アタッカー役のみ」は、その決定と矛盾する。
- `2026-07-29-cpu-air-shot-physics-alignment-design.md` 12節は、#85で
  `PlayerMovement`、`_jump_will_meet()`、`_sweet_jump_plan()`、AND条件を扱うとしている。
  即時フォールバックだけへAND条件を掛ける範囲縮小は行わない。

`46fbbf9` の製品コードを、固定seed 0/0、サーブ側交互、試合ごとにtickを977ずつずらし、
`tests/zz_toss_cause.gd` でCPU同士16試合x4000tick再測定した。最強CPUの空中打撃判断は
1472回（アタック456、トス1016）で、この測定条件ではトス打点1016回が全て
ネット上端より高かった。これは観測値であり、不変条件ではない。

ユーザーが次を確定するまで、条件式の実装へ進まない。

1. x4と未検証の約30fps仮定を使い、横距離80px・横速度10px/tick・縦速度5px/tickを採るか。
2. 高さを床から保存して `ball_y < 232` とするか、絶対値 `ball_y < 200` とするか。
3. 後発の承認済み役割設計どおり、アタッカー優先と会合不能時の代行を維持するか。

実装後は一理由ずつ差分を分け、正規入口の全件と同じ基準計測を毎回取り直す。
