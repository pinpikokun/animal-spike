# #85 CPUのジャンプ発火条件を原作のAND判定へ絞る（完了・2026-07-29）

**中身**: 原作は「頂点付近 AND 横に流れていない AND 十分高い」のANDで跳ぶ球を選び、
悪い球には跳ばない。現行は「会合できるか」だけを見ており、悪い球でも跳ぶ。

**根拠**: 実測。原作資料の5節（0x8824）の条件（横20px以内、|ball_vx|<5、
|ball_vy|<しきい値10、ball_y<200、かつアタッカー役のみ）を自分で読んでいる。

**なぜ着手したか**: #82 と同じ「打つ前に弾く」系。まとめてやると効率が良い。
単独でも「変な球に跳んで自滅する」を減らせる。

## 設計調査と承認（2026-07-29）

**状態: 完了。** 原作のAND構造、横距離、高さ、役割は根拠を追跡済みで、
速度10px/tick・5px/tickだけが未検証の時間換算を含む設計判断である。

- 横距離 `0x14` は原作の内部20目盛りである。承認済み換算
  `docs/superpowers/specs/2026-07-25-cpu-positioning-redesign.md` 4A.1では
  x方向を4倍するため、本作では80pxになる。この文書の「20px」と矛盾する。
- `docs/reference/original-vb22-physics.md` 1・2節では、原作の速度は座標へ毎フレーム加える
  値で、xは1目盛り約4px、yは1目盛り約1ラインである。既存の約30fps仮定から
  本作の60tick/sへ時間換算する候補値は、`|ball_vx| < 10px/tick`、
  `|ball_vy| < 5px/tick` となる。これは実機fps未確認のため確定値ではない。
- 原作コードの `ball_update()` は `0x0E6A` を毎回減らし、0の回だけ本体を更新して
  `0x0E6C` を再装填する。通常値2は外側ループ2周に1回、高速状態の値1は毎周更新を
  意味する。ただし通常試合ループにはタイマ待ち・垂直同期待ちがなく、入力読取中の
  固定CPUサイクル遅延しか確認できない。したがって毎秒の更新回数と約30fps仮定は
  静的解析では確定せず、上記10px/tick・5px/tickは時間換算を採る設計判断である。
- 本作の通常トス初速は上向き約-7.8px/tickである。縦条件を換算せず
  `|ball_vy| < 10px/tick` とすると、投げた直後から通って頂点付近という効果が成立しない、
  という導出になる。現行の重力で単独計算すると、通常トスの頂点は24tick目で、
  5px/tick未満は9〜40tick目の32tick、10px/tick未満は1〜55tick目の55tick通る。
- 原作の汎用描画 `0x292E` は `ball_y` を補正せず低水準描画 `0x00FA` へ渡し、
  `0x00FA` はVRAM先を `y * 80 + x` とする。原作 `ball_y` は32pxセルの上端である。
  通常球4コマの不透明部はセル内y=2〜28、現行の28px通常球はy=1〜26で中心配置される。
  可視上端を一致させると `current_y - 13 = original_y + 2`、すなわち現行中心は原作上端+15。
  よって原作の厳密な `ball_y < 200` は本作の `ball_y < 215` に対応する。静止時も原作
  `291 + 2 = 293`、本作 `306 - 13 = 293` で可視上端が一致する。以前の232案は原作の
  プレイヤーy=288を足元と誤読した値であり、実際は同じ描画へ渡す32pxセル上端なので撤回する。
  特殊球の透明余白は異なるが、物理・AI条件を表示コマごとに変えず通常球基準で固定する。
- 承認済み役割設計はアタッカーを禁止でなく優先権とし、役持ちが会合不能なら相方の代行を
  許可している。この文書の「アタッカー役のみ」は、その決定と矛盾する。
- `2026-07-29-cpu-air-shot-physics-alignment-design.md` 12節は、#85で
  `PlayerMovement`、`_jump_will_meet()`、`_sweet_jump_plan()`、AND条件を扱うとしている。
  即時フォールバックだけへAND条件を掛ける範囲縮小は行わない。

`46fbbf9` の製品コードを、固定seed 0/0、サーブ側交互、試合ごとにtickを977ずつずらし、
`tests/zz_toss_cause.gd` でCPU同士16試合x4000tick再測定した。最強CPUの空中打撃判断は
1472回（アタック456、トス1016）で、この測定条件ではトス打点1016回が全て
ネット上端より高かった。これは観測値であり、不変条件ではない。

同じ16試合x4000tickで、現行が自チームの上げ球へ実際にジャンプ入力を出した地上判断を
追加計測した。192回のうち、横距離80px・横速度10px/tick・縦速度5px/tick・高さ215を
全て通るものは88回だった。高さ215だけの不合格は24回である。各不合格数は他条件と
重複する観測値であり、導入後の保証値ではない。

この旧計測は後のClaude Code査読で、`tick` が現行乱数列へ影響せず、固定seed 0/0の
16試合はサーブ側2パターンの反復だったと判明した。数値は調査時の観測として残すが、
最終の導入前後比較には使わない。

横距離80pxは承認済みx4換算、高さ215は表示アンカー換算から一意に決まり、
アタッカー優先と会合不能時の代行は後発のユーザー決定である。これらは変更しない。

ユーザーはCodexとClaude Codeの双方がOKなら進行してよいと承認した。両者は、
横距離80px・横速度10px/tick・縦速度5px/tick・高さ215、アタッカー優先と
会合不能時の代行維持を一組の発火ゲートとして採ることへ最終合意した。

承認設計書は `docs/superpowers/specs/2026-07-29-cpu-jump-trigger-and-gate-design.md`。
承認版は122行、SHA-256
`ae1fded7b91d715863547caa5f04f58763c6696436d51d011202c29ff635e791` である。
