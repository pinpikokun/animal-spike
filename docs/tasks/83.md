## ゲート

`tests/unit/test_zz_performance.gd` は `test_` 関数を正確に1個だけ持ち、
成功・失敗にかかわらず `PERF_GATE` 集計を正確に1行出す。

### ロールバックstep

決定的な保存済み2チーム入力を計測外で生成する。各サンプルは実ロスター、全選手
`PRESET_MAX`、seed 0、勝利点999の新品stateを使い、600step暖機後に次を2000回測る。

1. `Simulation.tick()`
2. `to_int_array()`、`state_hash()`、snapshot Dictionary生成

5サンプルの最小値を合否、中央値を診断に使う。

- step上限: 230,000ns
- `load_int_array()` を含む16コマ下限見積り上限: 8,333,333ns

SyncManagerのグループ走査、欠損入力予測、frame生成、signal、buffer resizeは計測外で、
SimRoot担当範囲の下限ゲートである。

### 3候補空中仮想打球

政策3の固定fixtureで、productionの `_air_spike_candidate()` が手前・中央・奥の3本とも
非空であることと、`_decide_air_hit()` が両相手から最遠の奥候補を返すことを検査する。
1000回暖機後、5サンプル各5000回を測る。

- 下限: 5,000ns
- 上限: 54,000ns（#82完了後の締め直し。実測と承認式は下記参照）

戻り値は整数へ加算して消費し、fixture崩壊や計測蒸発を緑で通さない。

## 2026-08-03 ジャンプ打点予測追加後の再承認

原作8キャラのジャンプ高度対応で、CPUの空中打球候補を本番と同じ
「入力決定、選手移動、接触」の順序で評価するよう変更した。
方向キーは空中移動と打ち分けを兼ねるため、移動前の座標を使う旧評価では
予測した打点と実打点がずれ、HITOの一部アタックサーブが自陣へ落ちた。

`PlayerMovement.predict_air_contact_positions()` で3候補の同tick移動後座標を
一括計算し、その座標から接触距離を再計算する。人間側のジャンプ高度をCPU都合で
補正せず、本番移動との一致検査と原作8キャラの実サーブ通過検査を追加した。

この正確な予測により恒久fixtureの処理内容が増え、旧54,000nsを超えた。
状態全複製案は最小355,982nsのため棄却し、副作用なしの座標予測へ変更した。
試合全体のstepは全回230,000ns以内だった。

正規入口を独立5プロセスで測定した結果:

| プロセス | step最小ns | air最小ns |
|---:|---:|---:|
| 1 | 210,716 | 59,223 |
| 2 | 215,787 | 56,268 |
| 3 | 212,392 | 59,220 |
| 4 | 219,441 | 62,249 |
| 5 | 225,980 | 59,219 |

再承認式:

```text
max(process_min_ns) = 62,249
62,249 * 1.20 = 74,698.8
ceil(74,698.8 / 1,000) * 1,000 = 75,000ns
```

2026-08-03、ユーザーは処理内容、実測約0.062ms、60FPSの1フレーム約16.7msとの
比較説明を確認し、上限75,000nsへの更新を承認した。これは処理を遅くする目標値ではなく、
正確な同tick打点予測を含む新しい処理内容に対する回帰警報である。
