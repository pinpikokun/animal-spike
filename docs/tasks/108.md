# #108 テストランナーの偽PASS防御に穴がある

## 症状

**SCRIPT ERROR を出しているテストが PASS と表示される。**

`tests/run_tests.gd` は「1回も `check()` していないテストは FAIL」という防御
（`checks_run == 0`）を持つ。これは「ランタイムエラーでテストが黙って中断する」
事故を捕まえるためのものだが、**捕まえられるのは「1回も check していない場合」だけ**。

次の形は素通りする。

1. 事前条件用の `check()` が1回以上**成功**する
2. その後、本命の式の評価中に GDScript ランタイムエラーが起きる
3. テストメソッドが**関数ごと中断**し、`failures` は空のまま戻る
4. ランナーは `checks_run > 0` かつ `failures.is_empty()` を見て **PASS** と表示する

## 実測（2026-07-28、#105 の実装中に発見）

`tests/unit/test_boot_seed.gd` が、事前ガード関数で `check()` を2回成功させた後、
本命の行で `Invalid access to property or key 'aitick' on a base object of type 'Nil'`
を起こした。

```
SCRIPT ERROR: Invalid access to property or key 'aitick' on a base object of type 'Nil'.
   at: test_game_view_consumes_boot_seed_and_external_state_is_untouched
       (res://tests/unit/test_boot_seed.gd:43)
PASS  test_boot_seed.gd.test_game_view_consumes_boot_seed_and_external_state_is_untouched
```

Godot 単体の結果は **`461 tests, 0 failed` / exit code 0** だった。

## 救ったのは二段目の防御

`run_tests.ps1` の SCRIPT ERROR 検査が **exit code 1** を返して止めた。
`run_tests.gd` 冒頭コメントが謳う「二重防御」が設計どおり働いた。

**したがって現状でも実害は出にくい。** GDScript のランタイムエラーは必ず
SCRIPT ERROR を出すので、二段目が拾う。だが**一段目が「緑」と言うこと自体が
危険**で、Godot を直接叩いた人は騙される。

## 決めること

1. **一段目でも捕まえられるようにするか。** 候補:
   - 各テストの期待 check 回数を宣言させる（書くのが重い）
   - `check()` の呼び出し位置を記録し、最後の `check()` 以降に中断した形を検出する
   - ガード専用の `require()` を用意し、`checks_run` に数えない
     （事前条件と本命の検査を区別する。いちばん素直か）
2. **合否の正規の入口を文書化するか。** #105 の設計書は
   「`run_tests.ps1` の終了コードを正とする。Godot 単体の表示だけを合格証拠に
   してはならない」と決めた。これを `AGENTS.md` / `CLAUDE.md` 側の常設ルールへ
   上げるかどうか。

## 着手の前提

急がない。二段目が効いているので実害は限定的。
ただし**「緑は健全さの証拠ではない」という本プロジェクトの中心テーマそのもの**
なので、放置はしない。
