# 1. #86 決定論乱数のハッシュ実装が2種類ある＋使われないsaltがある

**中身**: 同じ役目のハッシュ関数が2つあり、式が違う。
`sim_cpu.gd:87 _noise()` はキーが `last_hit_tick`、actor項が `actor*998244353`。
`hit_resolver.gd:600 _keyed_hash()` はキーが `s.tick`、actor項が `(actor+1)*998244353`。
salt空間も別管理（1〜6 と 23/29/31）。
さらに **`SALT_RECEIVE`(=4) はゲーム本体で一度も使われておらず、テストだけが使っている。**
そのテストは「その抽選が成功する種」を探して前提を作っているが、
本体はその salt を引かないので、**テストが名前どおりの状況を作れている保証がない。**

**根拠**: 実測。salt の全定義と `_noise` / `_keyed_hash` の実装、
`SALT_RECEIVE` の参照箇所（テスト2箇所のみ）を確認。
**当初「salt=17 が重複」と書いたのは誤りで、現在のコードに重複は無い。訂正済み。**

**挙動不変で統合できることを実測で確認した（2026-07-27）**:
`tick 0..499 × actor 0..3 × salt 11種 = 22000件` を照合し、**不一致0件**。

```
HitResolver._keyed_hash(s, actor, salt) == SimCpu._noise(salt, s.tick, actor + 1)
salt の重複: 無し（sim_cpu 1..8 / hit_resolver 23,29,31）
```

混合部は完全に同一で、違いは**キーの出所**（`last_hit_tick` か `s.tick` か）と
**actor に +1 するか**だけ。`_hash(key, salt, actor_term)` 1本にまとめ、
呼び出し側が従来と同じ引数を渡せば**乱数値は1つも変わらない**。

**統合するのは「式」であって「役目」ではない（2026-07-27 追記）**。
原作調査（`docs/tasks/88.md` の (e-2)）で、この2つは**役目が違う**ことが判明した。
`last_hit_tick` 側は**打球ごとに変わる**＝原作の `aitick` 相当、`s.tick` 側は
**フレームごとに変わる**＝原作の `RND` 相当。原作もこの2つを用途で使い分けている。
**キーの出所は絶対に混ぜないこと。** 当初この見出しに書いた「同じ役目のハッシュが
2つある」は正確でなく、**別の役目のハッシュが、たまたま同じ式で書かれている**が正しい。
**ゴールデンハッシュの張り替えは不要。** よって #88 と1本化する必要はなく、
「緑の足場のまま通せる掃除」として #88 の前に単独で実施できる。

**統合の形（2026-07-27 決定。Codex と合意）**:

- 新規ファイル `src/sim/sim_rng.gd` を作り、混合式を**1本だけ**置く。
  他は `const SimRng := preload("res://src/sim/sim_rng.gd")` で参照する
  （このリポジトリは `class_name` を使わず preload で参照する慣習）
- 署名は `static func keyed_hash(key: int, salt: int, actor_term: int) -> int`。
  **`hash` という名前は使わない**（GDScript の組み込みと紛らわしい）
- 呼び出し側は従来と同じ引数を渡す。`SimCpu._noise(salt, key, actor)` は
  `SimRng.keyed_hash(key, salt, actor)`、`HitResolver._keyed_hash(s, actor, salt)` は
  `SimRng.keyed_hash(s.tick, salt, actor + 1)`。**乱数値は1つも変わらない**
- 効果は「**乱数アルゴリズムの置き場の一本化**」であって、#88 の工事がこの1ファイルに
  閉じるわけではない（#88 は `SimState`・更新位置・保存復元・同期ハッシュ・
  呼び出し側にも及ぶ。Codex の指摘）
- **salt の数値は #86 では絶対に変えない。** 廃止・維持・置換は #88 の契約で決める
- **`SALT_RECEIVE`(=4) は #86 では削除しない**（2026-07-28 に判断を撤回。下記）
- `SALT_AIR_SHOT`(=8) は #82 の剥離で消えた。**復活させない**（#82 の再設計時に決める）。
  現行の salt は `1..7` と `23/29/31`

**`SALT_RECEIVE` の削除を撤回した理由（2026-07-28。Codex の現物照合で判明）**:

当初は「本体が引かない salt を使う偽のテストなので、依存テストごと削除する」と決めた。
**しかし削除は挙動不変と両立しない。**

```gdscript
func _select_successful_roll(s, actor: int, salt: int, threshold: int) -> void:
	for key in 900:
		if SimCpu._noise(salt, key, actor) % 256 < threshold:
			s.last_hit_tick = key   # ← ここ
			return
```

このヘルパーは **`s.last_hit_tick` を書き換える**。つまり `SALT_RECEIVE` での呼び出しは
「引かれない抽選を成立させる」だけでなく、**`last_hit_tick` を特定の値に固定する副作用**を
持つ。`last_hit_tick` は `SALT_SWEET` など**本体が実際に引く抽選のキー**なので、
この呼び出しを消すと**他の抽選の出目が変わり、依存6本の前提が崩れる**
（`_incoming_attack_world()` を使う5本 +
`test_max_cpu_keeps_walking_when_horizontal_range_hides_ellipse_miss`）。

**#86 では定義を残し、「本体では一度も引かれず、テストだけが `last_hit_tick` を
固定するために使っている」ことをコメントで明記するに留める。**
是正は #88 のテスト三層へ送る。そこでは「初期乱数状態を直接与える」書き方になるので、
**種を探す前提作りごと消える。**

**なぜP1か**: テストの前提が実際の分岐と対応していないのは、
「通っているが何も守っていないテスト」を作る。これは他の全ての作業の土台を腐らせる。
かつ #88 の移行でどうせ両方のハッシュを触るので、その前に整理しておく方が安い。
