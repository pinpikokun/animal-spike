# 2. #88 決定論乱数をステートフル方式へ移行する（設計ミスの是正）

**中身**: いまの乱数は「状態を持たず、キーから毎回計算する」方式。
業界標準は「乱数の内部状態をゲーム状態に含めて巻き戻す」方式。
自前のステートフル乱数を書き、その状態を `SimState` の整数フィールドとして持つ。
移行対象はレシーブの散り / むらっけ / 狙い誤差 / ミス抽選 / ジャスト抽選 /
攻撃抽選 / 必殺技抽選 / ブロックのばらつき / トス低軌道 / 役割抽選。

**根拠**: 実測。GGPO 公式ドキュメントの該当節を自分で取得し
"the state of the random number generator is included in your game state" を確認。
Godot のロールバックアドオンの `NetworkRandomNumberGenerator.gd` を読み、
`_save_state` / `_load_state` で内部状態を保存・復元していることを確認。

**移行する理由の訂正（2026-07-27）**: 当初ここに
「Claude Code が業界標準を調べずに選んだ**誤設計**の是正」と書いたが、**言い過ぎだった**。
ステートレスなキー付きハッシュも、正しく設計すれば決定論的でロールバック安全であり、
方式そのものは誤りではない（Codex の指摘。妥当と判断して受け入れた）。

**移行する本当の理由は原作準拠。** 原作の乱数は
`RND = RND*7 + 0x4017 + aitick` を**毎フレーム1回**更新するステートフル方式
（`vb2211-analysis/snippets/vb22-cpu-rng.asm`、`0xC263`）。`aitick` 自体も
役割入替で `++`、打球時に `+= RND` で回り続ける。**2つの状態が混ざり合う。**

**#82 でサーブが壊れた直接の原因も方式ではなくキー選択**だった
（`s.last_hit_tick` 単独では、試合開始1本目が必ず tick 61 で固定される）。
ステートレスのままでも安定したイベントIDを足せば直せる。それでも移行するのは、
原作が毎フレーム更新であること、#84 の能力許可抽選も同じ乱数系列に乗ること、
#82 だけ暫定キーを足すと近く破棄する仕様とテストを承認することになるため。

## 原作の乱数の全体像（2026-07-27 実測。逆アセンブル全文を走査）

**`RND`（`0x1108`, word）への書き込みは全体で3箇所しかない。読み出しは30箇所以上あるが、
そのすべてが `mov ax, word ptr [0x1108]` = 読むだけで進めない。**

| 番地 | 何をするか | 位置づけ |
|---|---|---|
| `0xC26A` / `0xC276` | `RND = RND*7 + 0x4017 + aitick` | **毎フレーム1回**の更新 |
| `0xBBD2` | `RND = RND*2 + 1` してから `% 9` | **役割抽選だけの例外**（`role_assign` `0xBB40..0xBC80`） |

**(a) 原作には実質「消費順」が無い。**
役割抽選を除く全ての抽選は、そのフレームの `RND` を読むだけ。同一フレーム内では
全員が同じ値を見る。`RND%8` / `RND%4` / `RND%3` / `RND%2` と**法を変えて散らしている**。
したがって当初ここに書いた懸念「**乱数の消費順そのものがゲーム仕様になるため、
1箇所の抽選追加で以降の全CPU判断が変わる**」は、**原作方式を採る限り発生しない。**
抽選箇所を足しても系列は乱れず、ロールバックも2ワードの保存で足りる。

**(b) 唯一の例外が役割抽選。** `role_assign` は読んだあと `RND*2+1` を書き戻してから
`% 9` を取り、結果で `P_aiflag`（`0x118E`。bit0=前後役 / bit1=アタッカー役 /
bit2=ブロッカー役）に `or 6` / `or 4` を立てる。**本作の `_is_rally_attacker` /
`_is_rally_blocker` が `% 9` を使っているのは、この原作の写しとして正しい。**
同一フレームで2チーム分を引くため、ここだけは進めないと両チームが同じ役になる。

**(b-2) 役割抽選の分岐表は、本作が原作を正確に写している（2026-07-27 照合）。**
`0xBBE2..0xBC72` の飛び先を全て解読し、`P_aiflag` の bit1(=アタッカー)/bit2(=ブロッカー)
の立て方を表にした結果、本作の `_is_rally_attacker` / `_is_rally_blocker` と**完全一致**。

| | 原作 `RND%9` | 本作の記述 |
|---|---|---|
| アタッカーが slot0 | {0, 1, 5, 8} | `0,1,5,8: return slot == 0` |
| ブロッカーが2人とも | {0, 2, 5, 8} | `0,2,5,8: return true` |
| ブロッカーが slot0 だけ | {1, 4, 7} | `1,4,7: return slot == 0` |
| ブロッカー無し | {3, 6} | `_: return false` |

**移行時に変えるのは `% 9` の入力だけ。** 本作は `_noise(SALT_ROLE, s.rally_seq, team)`
＝ラリー番号とチームから毎回計算しているが、原作は `rng` を進めた値を使い、
**2チーム分をループで続けて引く**（`[bp-6]` が 0,1）。#88 ではこの消費の仕方へ寄せる。

**(c) 実質2系列で、互いに混ざる。**
`aitick`（`0x0EB8`, word）は**イベント駆動**で、役割入替で `++`、打球時に
`aitick += RND`（`0x39C2`）。難易度表では `aitick%8==0`（EASY のスパイクジャンプ）と
`RND%4==0`（NORMAL の地上必殺技）が**用途によって使い分けられている。**

**(d) 種は起動時のシステム時刻。`0x9C00` で1回だけ。**

```
9c00  b42c        mov ah, 0x2c        ; DOS INT 21h AH=2Ch = システム時刻取得
9c02  cd21        int 0x21            ;   戻り CH=時 CL=分 DH=秒 DL=1/100秒
9c04  890e0811    mov [RND], cx       ; RND = (時 << 8) | 分
9c08  a10811      mov ax, [RND]
9c0b  a3b80e      mov [aitick], ax    ; aitick = RND
```

`aitick` への書き込みも全体で3箇所しかなく（`0x39DA` の `+= RND`、`0x7F1D` の `++`、
そしてこの `0x9C0B`）、**3箇所すべての正体が判明している。**

したがって **試合・セット・ラリーのどこにも再初期化は無い。** 起動から終了まで
2ワードが回り続ける。これは #82 で見つけた「`s.tick` がラリーを跨いでもリセット
されない」と同じ性質で、原作では意図的にそうなっている。

**種の粒度は「時と分」だけ**である点に注意。同じ分のうちに起動し直すと
**まったく同じ乱数列**が出る。

**(d-2) 本作では時刻を種にできない。** ロールバックネットコードは両ピアで同じ
乱数列を要求し、テストは固定種で再現できる必要がある。**種は「試合開始時に決まる
整数」として `SimState` に持ち、`reset_match` で設定する**（対戦では交換、
ローカルでは任意、テストでは固定）。これは原作の仕組みではなく本作の要請による
置き換えなので、#88 の設計書で明示すること。

**(e-0) 原作でも試合開始直後の展開は種次第で毎回同じ**になりうる構造で、
人間の打球タイミングが `aitick += RND` を通じて系列を散らす。

**(e) 副作用**: 同一フレームに複数CPUが判断すると全員が同じ `RND` を読むため、
`%2` のような分岐は**両者が同じ側へ倒れる**。原作はこれを許容している。

---

**(e-2) 2系列は用途で綺麗に分かれている。しかも本作の現行2実装がそれに対応している。**

原作の難易度テーブル（`0x7F30` / `0x7F5E` / `0x7FCA` / `0x800C`）を見ると:

| 原作の用途 | 使う変数 | 法 |
|---|---|---|
| 攻撃球へのレシーブ許可 | `aitick` | %8 / %4 / %3 |
| スパイク用ジャンプ許可 | `aitick` | %8 / %2 / %3 |
| ブロック用ジャンプ許可 | `aitick` | %6 / %3 |
| 地上必殺技の許可 | `aitick` と `RND` の混在 | %8 / %4 / %3 |
| 特定硬直の無視 | `RND` | %4 / %3 / %2 |
| 3打目のレシーブ許可（`0x80CE`） | `RND` | %6 |
| 役割抽選（唯一進める） | `RND` | %9 |

**`aitick` は打球ごとに `+= RND` で大きく飛ぶので「その打球の間は同じ判断」、
`RND` は毎フレーム変わるので「毎フレーム振り直す」。** 使い分けに意味がある。

本作の現行実装はこうなっている:

| 本作の現行 | キーの出所 | 変わる粒度 | 原作の対応 |
|---|---|---|---|
| `SimCpu._roll` → `_noise(salt, s.last_hit_tick, actor)` | `last_hit_tick` | **打球ごと** | `aitick` |
| `HitResolver._keyed_hash(s, actor, salt)` | `s.tick` | **フレームごと** | `RND` |

**式が同じで役目が違う。** #86 で統合するのは**式**であって役目ではない。
キーの出所（`last_hit_tick` か `s.tick` か）が2系列の区別そのものなので、
#86 では絶対に混ぜないこと。#88 でもこの対応を保存して移行する。

**(f) 更新は無条件。停止中も進む。**
原作の `0xC263` は `game_main` のループ内にあり、直前が描画呼び出し、直後がフェーズ処理。
**フェーズや停止状態を見る前に更新している**ので、止まっている間も乱数は回り続ける。

本作の `Simulation.tick()` は `_handle_switch` → **CPU思考を4人分生成** → `step()`
（`state.tick += 1` → 物理）の順。`step()` は `hit_freeze` / `slow_ticks` で
早期 return する。**乱数の更新は `tick()` の先頭、この早期 return より前に置く**こと。
原作が無条件に回すのと揃い、ヒットストップやスローモーション中も乱数が進む。

---

**移行時に契約で固定すること（実装者に選ばせない）**:
更新周期（毎フレームのどの位置で1回進めるか）／初期状態／消費（読むだけか進めるか）／
保存・復元／同期ハッシュの対象／**単一系列にするか用途別系列に分けるか**／
同一tickに打球と役割入替が重なったときの `aitick` の更新順。

**テストは三層に作り直す**（「その抽選が当たる種を総当たりで探す」書き方は捨てる）:
PRNG単体（既知の状態から次の状態と出力）／抽選単体（初期乱数状態を直接与えて各分岐）／
シナリオ（固定初期状態から所定tickまで進め、ロールバック前後の一致）。

**なぜP1か**: **機能追加ではなく土台の是正。**
抽選を書く箇所が増えるほど移行が重くなる。いま10箇所だが、キャラと必殺技が増えれば倍になる。
ユーザーも「将来を見据えた設計は先にやるべき」と明示している。
なお #86 を先にやってキー空間を整理してから着手する。
