# P0 — 今やる（4件）

## 1. #100 ネットを越えて相手コートへ返す球を作り直す（設計完了・実装未着手）

**中身**: サーブ（トスサーブ）と3打目の返球を、原作と同じ「速度を直接決める」方式にする。
今は落下点を決めて速度を逆算しており、**相手コートに入る保証が無い。**
落ちる場所は立ち位置・打点の高さ・入射・トス上手下手の4つで変える（乱数ではない）。
3打目の強制（原作 `0x56CF`）と、自陣トスの落下点を原作へ戻すのも同時にやる。

**設計書**: `docs/superpowers/specs/2026-07-26-return-over-net-design.md`。**ユーザー承認済み。**

**根拠**: 実測。自陣トスの落下点を原作の値へ変えたところ、
同じ設定が敵陣側も動かしていたため **CPUのサーブがネットに当たって越えなくなった**
（`test_cpu_serve_crosses_net` が落ちた）。今の数値でたまたま成立しているだけと判明した。

**なぜP0か**: 今の作りは数値を1つ動かすと壊れる。しかも #66 第4段はCPUの打ち方を調整する作業で、
返球の作りが変わる前提で調整すると二度手間になる。**#66 第4段より先にやるとユーザーが決定。**

## 2. #66 CPU位置取り再設計（団子・味方妨害・人間の出番奪いを一括）

**中身**: 味方CPU同士が同じ球へ突っ込んで3タッチを超えて失点する、2体が団子になる、
味方CPUが全部自分でやって人間の出番が無い——この3つを一括で直す。
原作の4機構（ラリー単位の役割抽選 / 前衛後衛の持続役と定期スワップ /
ネット基準の退避 / 近接時の打撃抑制）をまとめて入れる。

**進捗（2026-07-26）**: 第1段（状態の土台）・第2段（役割抽選）・**第3段（原作の待機位置表）**
まで完了・プッシュ済み。残りは第4段（近接時の打撃抑制・ブロック寄せ・3タッチ時の移動停止・
味方は常に最強・最強の誤差ゼロ化）と第5段（固まるのをやめる・うろうろ・遅延短縮）。

**根拠**: 実測。CPU同士6試合で最強は試合の26%を相方と32px以内で過ごしている（弱は0%）。
4タッチ目の発生は最強で3回/6試合。第2段で4タッチ目は0回になった。

**なぜP0か**: 進行中で大半が終わっている。中途半端な状態で放置するのが一番まずい。
過去に部分導入して全指標が悪化し撤回した経緯があるため、途中で止められない。
かつユーザーが実プレイで繰り返し指摘している問題そのもの。

**注意**: 第4段の着手は **#100 の完了後**。順番はユーザー決定。

## 2. #91 ラリー再開で消えない状態＋ネット経路の設定検査漏れ

## 3. #83 性能の見張りテスト（1コマのコスト上限）

**中身**: 1コマのシミュレーションのコストが決めた上限を超えたらテストが落ちる仕組み。

# P1 — 土台。コードが増える前に（2件）

## 1. #86 決定論乱数のハッシュ実装が2種類ある＋使われないsaltがある

**中身**: 同じ役目のハッシュ関数が2つあり、式が違う。
`sim_cpu.gd:87 _noise()` はキーが `last_hit_tick`、actor項が `actor*998244353`。
`hit_resolver.gd:600 _keyed_hash()` はキーが `s.tick`、actor項が `(actor+1)*998244353`。
salt空間も別管理（1〜6 と 23/29/31）。
さらに **`SALT_RECEIVE`(=4) はゲーム本体で一度も使われておらず、テストだけが使っている。**
そのテストは「その抽選が成功する種」を探して前提を作っているが、
本体はその salt を引かないので、**テストが名前どおりの状況を作れている保証がない。**

**根拠**: 実測。salt の全定義と `_noise` / `_keyed_hash` の実装、
`SALT_RECEIVE` の参照箇所（テスト2箇所のみ）を確認。
**当初「salt=17 が重複」と書いたのは誤りで、現在のコードに重複は無い。訂正済み。**

**なぜP1か**: テストの前提が実際の分岐と対応していないのは、
「通っているが何も守っていないテスト」を作る。これは他の全ての作業の土台を腐らせる。
かつ #88 の移行でどうせ両方のハッシュを触るので、その前に整理しておく方が安い。

## 2. #88 決定論乱数をステートフル方式へ移行する（設計ミスの是正）

**中身**: いまの乱数は「状態を持たず、キーから毎回計算する」方式。
業界標準は「乱数の内部状態をゲーム状態に含めて巻き戻す」方式。
自前のステートフル乱数を書き、その状態を `SimState` の整数フィールドとして持つ。
移行対象はレシーブの散り / むらっけ / 狙い誤差 / ミス抽選 / ジャスト抽選 /
攻撃抽選 / 必殺技抽選 / ブロックのばらつき / トス低軌道 / 役割抽選。

**根拠**: 実測。GGPO 公式ドキュメントの該当節を自分で取得し
"the state of the random number generator is included in your game state" を確認。
Godot のロールバックアドオンの `NetworkRandomNumberGenerator.gd` を読み、
`_save_state` / `_load_state` で内部状態を保存・復元していることを確認。

**なぜP1か**: **Claude Code が業界標準を調べずに選んだ設計の是正であり、機能追加ではない。**
抽選を書く箇所が増えるほど移行が重くなる。いま10箇所だが、キャラと必殺技が増えれば倍になる。
ユーザーも「将来を見据えた設計は先にやるべき」と明示している。
なお #86 を先にやってキー空間を整理してから着手する。

# P2 — ゲームの中身。遊んだときの面白さ（8件）

## 0. #101 味方へ上げるトスの高さに駆け引きを作る（課題提起のみ・未設計）

**中身**: 現実のバレーでは、高いトスは打ちやすいが相手にタイミングを読まれてブロックされ、
低い速攻は打つのが難しいが読まれない、という交換が成立している。
本作ではこの交換が壊れる。交換は「打つのが難しい＝攻める側のコスト」と
「ブロックが間に合わない＝守る側の不利」の2つでできているが、
**CPUは計算でタイミングを合わせられるので前者が消え、後者の利点だけが残る。**
デメリットの無い選択肢は必ずそればかり使われ、駆け引きが死ぬ。

**課題文書**: `docs/superpowers/specs/2026-07-26-toss-height-tradeoff-issue.md`。
**設計していない。実装していない。着手時はまず設計会を開くこと。**

**根拠**: ユーザーの提起（2026-07-26）。**CPUが実際に速攻ばかり選ぶかは未計測。**

**なぜP2か**: 遊びの深さに直結する。ただし今のゲームが壊れているわけではないので急がない。
着手前に「そもそもこの駆け引きを入れるか」から決める（入れない判断もありうる）。

**注意**: これは**味方へ上げるトス**の話。**相手コートへ返す球（#100）とは別物。**
混同すると話が破綻する。

## 1. #80 味方CPUが全部自分でやり人間の出番がない

**中身**: 味方CPUが自分でレシーブして自分で前に出て自分でアタックまで完結してしまう。
原作は「1チームにつきそのラリーのアタッカーは必ず1人」の抽選で構造的に防いでいる。
採択した仕様は、役割を「禁止」でなく「優先権」として扱い、
役の人が届かないときはもう一人が打ってよい。加えて相方が人間のときだけ
「自分が上げたトスは自分で打たない」を適用する。

**根拠**: 実測。原作の役割抽選ルーチン（`role_assign` 0xBB40）の全9通りを逆アセンブルから解読。
アタッカー役はどの目でもちょうど1人で、両方がアタッカーになる目は存在しない。

**なぜP2の1位か**: #66 に統合済みで、#66 の完了と同時に解決する。
ユーザーが実プレイで最も強く訴えた問題の1つ。
