# CPU味方の位置取り再設計 (団子・3タッチ超過・人間の出番奪い・サービスエース)

Status: 設計・未実装 (2026-07-25)。

ユーザー指示 (2026-07-25): 団子・味方のアタック/トス妨害・人間の出番奪いの3件は
分離せず一括で設計して直す。これが片付いてから操作体系の原作準拠化へ進む。
サービスエースの常時穴も、原因が待機位置の固定にあると分かったため本書に統合する。

## 1. 解く問題

実プレイ報告3件は、いずれも「2体が同じ場所へ寄る」ことに起因する:

1. 味方CPU同士が互いの打球を邪魔し、3タッチを超えて失点する
2. 味方CPUが全部自分で完結し、人間が入り込む余地がない
3. 味方が団子で動く (タスク#66、過去に一度対処を試みて失敗)

### 実測 (2026-07-25、CPU同士6試合ずつ)

4タッチ目 (超えると必ず失点) が発生した瞬間のペア距離:

| 難易度 | 発生 | 発生時の距離 | 常時の距離 | 32px以内だった割合 |
|---|---|---|---|---|
| 弱 | 0回 | - | 101px | - |
| 普通 | 3回 | 30px | 78px | 33% |
| 強い | 5回 | 41px | 76px | 20% |
| 最強 | 4回 | **19px** | 73px | **100%** |

**最強では4回中4回が32px以内で起きている。重なっていない時には一度も起きない。**

「弱」だけが 0回・常時101px を達成している。弱は落下点予測 (AB_PREDICT) を
持たないため、2体が同じ予測点へ収束しない。**強くするほど重なるという逆転が
起きている。**

### 計測上の注意 (同じ誤りを繰り返さないため)

- 「連続で自チームが触った回数」を妨害の指標にしてはいけない。
  バレーボールでは3回まで連続で触るのが正常な組み立てであり、
  レシーブ→トス→アタックが全部これに該当する。2026-07-25に一度この誤りを犯した。
- 有効な指標は **4タッチ目の発生 (touches > max_touches への遷移)**。
  曖昧さがなく、必ず失点につながる。tick数ではなく発生回数で数えること。
- 「人間の出番を奪う」は棒立ちのダミー人間では測れない。動かない相手からは
  奪いようがないため。測るならボールへ歩く簡易人間を書くか、実プレイで判断する。

### 実測2 (2026-07-25 追記): 待機位置の継ぎ目が固定の穴になる

実プレイ報告「敵陣のちょうど真ん中(敵Aと敵Bの間)へ落とすサーブは、
最強CPU相手でも簡単にサービスエースになる」を計測で再現した。

計測方法 (`tests/zz_ace_map.gd` 相当。使い捨てなのでコミットしていない):
自陣ネット際からの通常アタック球の着弾xを 260〜488px の範囲で4px刻みに振り、
乱数の目 (`last_hit_tick`) を16通り変えて、敵チームが触れたかを数える
(1プリセットあたり 58着弾 x 16目 = 928試行)。
「16回中8回以上見送る着弾点」を **常時穴** と呼ぶ。

敵チームのホームは 前衛291px / 後衛392px。中間点は341.5px。

| 難易度 | 見送り率 | 常時穴 |
|---|---|---|
| 弱 | 37% | 264,268,336-364,448,452 |
| 普通 | 15% | 344,348,352,356 |
| 強い | 8% | 344,348 |
| 最強 | 4% | **344** |
| 最強(ミス抽選なし) | 1% | 344 |

読み取れること:

- **最強の見送り4%のうち3%は狙い誤差・ミス抽選そのもの** (`P_MISS`=8/256=3.1%)。
  これは「惜しい失敗」を意図的に入れている設計どおりの挙動で、バグではない。
- 残る構造的な穴は **344px の1点だけ**。位置は2人のホームの中間点と一致する。
- tick単位のトレースで確認した内訳: 飛行19tickのうち12tickが反応遅延で消え、
  残り7tickでは48pxを詰めきれない。**接触予測が1tick足りずに落球する。**
  譲り合いでも構え固まりでもなく、単純に間に合っていない。

つまりこれは **待機位置が固定で継ぎ目が動かない** という設計の帰結である。
人間は一度その座標を覚えれば毎回そこへ落とせるので、確率4%ではなく
「狙えば必ず入る一点」として体感される。原作の待機位置テーブル(下の2.4)は
`aitick % 9` で位置が変わるため、この意味での固定の継ぎ目を持たない。

#### 検証で外した仮説 (同じ道を再度通らないため)

1. **「ジャストレシーブの構えで固まって見送る」** — 構え経路の停止条件が
   水平距離だけで、実際の楕円判定と食い違う欠陥は実在した。修正して
   最強の見送りは 6%→4%、常時穴は3箇所→1箇所に改善した。
   ただし報告されたサービスエースの主因ではなかった。
2. **「役割分担のデッドロック」** — 落下点 `land_x` が狙い誤差とミス抽選で汚された後に
   担当を比べているため、汚れた側と汚れていない側で「両者譲り」が起きる、と考えた。
   両者が同じ未汚染の落下点で比べるよう変えて計測したが、
   最強 46/928 のまま変化なし。**採用しない。**
   (コードとしては対称化した方が筋は良いが、ゴールデンを壊す変更を
   計測できる利得なしに入れない、という判断)

計測上の注意 (追記): **乱数の目を1つだけ固定して測ってはいけない。**
`last_hit_tick` を1000に固定した最初の計測では、たまたまミス抽選が当たった目を見て
「修正で悪化した」と誤った結論を出した。16目に増やしたら改善だと分かった。
着弾点や難易度を比較するときは必ず複数の目で平均を取ること。

## 2. 原作の仕組み (一次資料)

`docs/reference/original-vb22-cpu-ai.md` (VB22.EXE逆アセンブル) の3節。
原作は4つの機構が組み合わさっている。**どれか1つだけ入れても効かない。**
2026-07-25以前に「非レシーバーを固定ポストへ退かせる」だけを試して全指標が
悪化し撤回した経緯がある。単独導入は再び失敗する。

### 2.1 前衛/後衛の持続的な役割 (P_aiflag bit0)

0x7E31 で毎フレーム「相方より前か後ろか」を更新し、
0x7E9D で `aitick % 8 == 0` ごとに相方と入れ替える。
**2人は常に前衛/後衛に分かれ、定期的にスワップする。**

### 2.2 アタッカー役/ブロッカー役はラリーごとの抽選 (P_aiflag bit1/bit2)

0xBBCC で `r = RND % 9` を引き、9通りの組み合わせから役を決める。
**両方がアタッカーになる組み合わせは限られる。跳ぶのは原則ひとり。**
これが「二人とも拾いに行って誰も攻めない」を構造的に潰している。

### 2.3 ボールを取る担当 (0x8319)

- 1打目は二人とも予測着弾へ突っ込む (idx>=2 は +4 ずらす)
- 相方が動作中なら自分が取る
- 距離比較は **相方の前フレーム位置** (`P_x_prev`) を使う。振動を抑える効果がある
- **相方が近い → 自分はネット際 (ネットから16px) へ退く。相方基準ではなくネット基準**
- 自分が取る → 目標 = 予測着弾 - (進行方向へ先回りする補正)
- **3回触っていたら動かない**
- **相方と8px以内 かつ 相方もCPU なら自分は打たない** (0x8229)

### 2.4 待機位置は時間で変わるテーブル (0x8406)

`aitick % 9` と前後役の組み合わせで、自コート中央からのオフセットを決める。
相方が動作中なら 40/64/16px、待機中なら前後役ごとに (20 or 60)/(35 or 70)/(15 or 40)px。
**同じ場所に固まらない。**

## 4. 採用する設計

原作の4機構をまとめて入れる。**部分導入は禁止**(過去に失敗済み)。

### 4.0 前提: 「相方が人間か」を本当に判定できるようにする

現行の `mate_is_human` は `mate_slot == controlled` だけで決まる(`sim_cpu.gd:666`)。
`controlled_l` / `controlled_r` は人間がいなくても必ずどちらかのスロットを指すので、
**CPUだけの敵チームでも、片方は「相方は人間だ」と誤認して非対称な規則を使っている。**
2026-07-25のサービスエース調査で発見した。

`SimState` に人間が操作しているチームのビットマスクを持たせ、
`mate_is_human = (mate_slot == controlled) and そのチームに人間がいる` にする。
既定値は「人間なし」。1人プレイの表示層(`game_view.gd` / `main.gd`)と
ネット対戦(`net_input_node.gd`)が自分のチームを立てる。
state_hash とシリアライズにも入れること。

同時に、4.1の「自分が上げたトスは自分で打たない」を判定するための土台も要る。
`SimState` は `last_touch_team` しか持っておらず、**最後に触ったのが誰かを記録していない**
(2026-07-25 確認)。最後に打球したプレイヤーの添字を保持するフィールドを追加する。

第1段で `SimState` へ入れるフィールドは3つ:

| フィールド | 意味 | 用途 |
|---|---|---|
| `human_team_mask` | 人間が操作しているチームのビットマスク | 4.1の部品3、4.7 |
| `rally_seq` | ラリーの通し番号 | 4.1の抽選キー |
| `last_touch_idx` | 最後に打球したプレイヤーの添字(0-3、無しは-1) | 4.1の「自分のトス」判定 |

これは4.1以降の前提であり、`mate_is_human` の修正以外では挙動を変えない。

### 4.1 ラリー単位の役割抽選

**採択された挙動 (2026-07-25 ユーザー決定)**

原作の逆アセンブル(`role_assign` 0xBB40)を全9通り解読した結果:

| 目 | 確率 | 割り当て |
|---|---|---|
| r=0,5,8 | 3/9 | a=アタッカー+ブロッカー / b=ブロッカー |
| r=1 | 1/9 | a=アタッカー+ブロッカー / b=なし |
| r=2 | 1/9 | a=ブロッカー / b=アタッカー+ブロッカー |
| r=3,6 | 2/9 | a=なし / b=アタッカー |
| r=4,7 | 2/9 | a=ブロッカー / b=アタッカー |

**アタッカー役はどの目でもちょうど1人。両方がアタッカーになる目は存在しない。**
(a が 4/9、b が 5/9)

採択する仕様:

1. ラリー開始時に、チームごとにアタッカー役1人とブロッカー役を決定論的に抽選する。
   上の分布をそのまま使う。
2. **アタッカー役は「禁止」ではなく「優先権」として扱う。**
   - 2人とも打てる位置にいる → 役を持つ方だけが跳ぶ。もう一人は譲る
   - **役を持つ方がボールに届かない → もう一人が打ってよい**
   「届かない」は曖昧語にしない。既存の会合予測 `_jump_will_meet()` で判定する。
   理由: 厳密禁止だと、人間が上げたトスを味方が引いていないラリーで
   スパイクが緩い返球に化ける。3打目は自動的にネットを越える(`sim_cpu.gd:631`)ので
   ラリーは死なないが、次に相手が楽に攻めてくる不利が残る。
3. **自分が上げたトスは自分で打たない。ただし相方が人間のチームでだけ適用する。**
   原作には無い追加規則。ユーザー要望
   「味方がレシーブして前に出したなら人間に打たせてほしい」に直接対応する。
   CPU同士のチーム(敵チーム)には適用しない。4.0のマスクで分岐する。

決定論の制約: 逐次PRNGは使えない。既存の keyed hash 方式
(`_noise(salt, key, actor)`) を使い、キーは `rally_seq`、actor はチーム番号にする。
**役割は状態として保存しない。** `rally_seq` とチームから毎回引き直せば常に同じ答えが出るので、
`SimState` にフラグを増やす必要がない。ラリーが変われば `rally_seq` が変わり、役も変わる。

「自分が上げたトス」は `last_touch_idx` が自分と一致するかで判定する。

**リスクと対策**: 2の「届かないなら打ってよい」を緩く作ると、結局2人とも
打ちに行って現状へ戻る。実装後に**2人が同じ球に跳んだ回数**を測り、
増えていないことを確認する。増えていたら判定を締める。

### 4.2 非レシーバーはネット基準の固定ゾーンへ退く

`_cover_target()` の `mate.x ± spacing` を廃し、**コート内の固定ゾーン**を持たせる。
前衛役はネット寄り、後衛役は壁寄り。相方の位置に追従させない。

### 4.3 前衛/後衛の役割と定期スワップ

前衛/後衛を状態として持ち、一定間隔で入れ替える。
毎フレームの距離比較で役が反転しないようにする。

### 4.4 近接時の打撃抑制を効かせる

相方が一定距離以内かつ相方もCPUなら打撃入力を出さない。
**「リーチ内は必ず拾う」上書き(`sim_cpu.gd:694`付近)を、この抑制より弱くする。**
現状はこの1行が役割分担を無効化している。

### 4.7 味方CPUの強さは難易度に依存しない

**採択 (2026-07-25 ユーザー決定)。原作準拠。**

原作は `0xB561` で「相方が人間なら P_skill を常に 3 (SUPER)」にしており、
GAME LEVEL は敵チームにしか掛からない(参考資料 7節)。これに合わせる。

人間のいるチームの味方CPUは、選択された難易度によらず最強プロファイルを使う。
難易度は敵チームにだけ掛ける。弱い難易度で遊んでも味方が足を引っ張らない。
出しゃばりは4.1の役割抽選で抑えるので、味方を弱くする必要がない。

判定には4.0のマスクを使う。

### 4.5 3タッチ時は移動も止める

自チームが上限まで触っていたら、追加の追いかけをしない。

### 4.6 待機位置を時間で振り、継ぎ目を固定しない

原作の待機位置テーブル(2.4)を移植する。2人のホームが常に同じ座標だと、
その中間点が「狙えば必ず入る一点」になる(実測2)。
テーブル方式なら継ぎ目が時間とともに動くので、同じ座標を撃ち続けても通らなくなる。

これは4.2(ネット基準の退避ゾーン)と同じ関数で決まるべきもので、
別々に実装しないこと。退避先 = 「前後役 x aitick相当のフェーズ」で引くテーブル、が形。

## 4A. 原作から確定した数値の一覧 (2026-07-25 逆アセンブルで直接確認)

**この節の目的**: 実装に使う数値をすべてここに集め、1つずつ出典を書く。
出典の無い数値を実装に入れない。これは 2026-07-25 にユーザーから受けた指示による。
それまで Claude Code は根拠のない数値を3回入れており(狙い誤差の方針、
役割の入替間隔180、待機位置の位相90)、すべてユーザーの指摘で発覚した。

### 4A.1 座標の換算率 (2026-07-26 全面訂正)

**原作の内部座標は画面ドットではない。** 横方向は 1目盛り = 画面4ドット。
PC-98 は横8ドットを1バイトで扱い、原作は内部 x を2で割ってバイト位置として渡すため
(`0xC301`)、画面上は内部値の4倍のドット数になる。
出典: `docs/reference/original-vb22-physics.md:38`「1単位≈4px」。

| 項目 | 原作(内部目盛り) | 原作(画面ドット) | 出典 |
|---|---|---|---|
| 左右の壁 | 4 と 148 | 16 と 592 | `0x455B` 壁反射 |
| ネット中央 | 76 (`0x4C`) | 304 | `0x8406` の `mov ax, 0x4C` |
| コート幅(壁から壁) | 144 | **576** | 上の2つの差 |

**本作のコート幅を 576px に合わせる**(2026-07-26 ユーザー決定。理由は 4B.8)。

**換算率 = 576 ÷ 144 = ちょうど 4。** 以後 `原作の目盛り × 4` で変換する。

**この換算率は x 方向にのみ使う。** 原作の y は 1目盛り = 1ライン
(`original-vb22-physics.md:39`)で倍率が違う。y へ流用しない。

#### 2026-07-26 に判明した誤りの記録 (再発防止)

**この節は 2026-07-25 版が全面的に誤っていた。** 何をどう間違えたかを残す。

| 誤り | 内容 |
|---|---|
| 換算率 2.947 | `224 ÷ 76` と、**原点の異なる絶対座標どうしを割った**。原作の壁は 4 から始まりコートは 0 から始まらない。幅どうしで割るのが正しい |
| 単位を px と表記 | 原作の内部値を「原作8px」等と書いた。**目盛りであって px ではない。**「1単位≈4px」は参照した資料の同じ行に書かれていたが読んでいなかった |
| 「裏取り」段落 | 「変換値が現行のホーム(前衛67px/後衛168px)と一致する。偶然では一致しない」と書いた。**照合相手の現行ホームは Claude Code が根拠なく置いた数値であり、証拠にならない。** 自作の数値と突き合わせて裏取りを主張した。削除した |
| キャラ寸法 | コードのコメントから「キャラ48px」と拾って断定した。実測は 22×29px(`assets/characters/*/walk/walk.png` は2コマ入りの 44×29) |

**この節に数値を足すときの規則**(上記の再発防止):

1. 数値だけでなく**単位**を書く。原作値は「目盛り」か「画面ドット」かを明記する
2. **掛け算そのものにも出典を書く。** 何と何を割ったのかを式で残す
3. 照合による裏取りは、**照合相手にも出典があるときだけ**有効。本作の既存値との
   一致は根拠にならない(既存値の多くが出典不明のため)
4. 寸法はコメントや記憶でなく**実測**する。測ったコマンドを残す

### 4A.2 aitick は時計ではない

| 場所 | 動作 | 出典 |
|---|---|---|
| `0x39C2` 打球発生時 | `aitick += RND` | `add word ptr [aitick], ax` |
| `0x7E9D` 役の入替時 | `aitick++` | シンボル表 `0x0EB8` |

**それ以外では増えない。時間が経っても進まない。**
したがって原作の `aitick % N` は「N フレームごと」ではなく
**「およそ N 打球に1回」** を意味する。

本作では `SimState` に打球回数のカウンタを追加してこれに対応させる。
時間(`s.tick`)を使わない。**これが 2026-07-25 の設計誤りの是正点。**

### 4A.3 待機位置テーブル (`0x8406`〜`0x85CF`)

計算式は共通で `目標x = ネットx - 向き × オフセット`。
**基準はコート中央ではなくネット。**
(旧記述「自コート中央からのオフセット」は誤り。2026-07-25 に訂正)

**分岐条件** (`0x82E9`): 相方の `P_state != 0` なら「相方が動作中」。
`P_state == 0` は地上待機。

**相方が動作中** (`0x841E` / `0x8438` / `0x8454`、前後役を見ない):

| `aitick%9` | 確率 | 原作(目盛り) | 本作 (`×4`) |
|---|---|---|---|
| 0,1,2,3,4 | 5/9 | 40 | **160** |
| 5,6 | 2/9 | 64 | **256** |
| 7,8 | 2/9 | 16 | **64** |

**相方が待機中** (`0x84CE` / `0x850C` / `0x854A`、オフセット = `bit0 × A + B`):

| `aitick%9` | 確率 | 原作 前衛 / 後衛 (目盛り) | 本作 前衛 / 後衛 (`×4`) |
|---|---|---|---|
| 0,1,2,3,8 | 5/9 | 20 / 60 | **80 / 240** |
| 4,5 | 2/9 | 35 / 70 | **140 / 280** |
| 6,7 | 2/9 | 15 / 40 | **60 / 160** |

`bit0` は `P_aiflag` の最下位ビット。`bit0=1` の側がネットから遠い = 後衛。

**オフセットの上限**: ネットから壁までは 72目盛り = 288px。
後衛の最大 280px は壁の 8px 手前で、コート内に収まる。

**この表が解く問題**: 2人の待機位置がラリーごとに動くため、
「そこへ落とせば必ず取れない」という固定の穴ができなくなる。
(2026-07-25 版に書かれていた「中間点81〜154px」「穴は25px幅」という記述は、
誤った換算率 2.947 で算出したもの。コート幅の変更もあり、実測しなおすまで数値は書かない)

### 4A.4 前衛/後衛の決め方 (`0x7E31`) と入れ替え (`0x7E9D`)

決め方: 自分の x と `相方の x + 向き×16` を比べ、ネットから遠い側が後衛(`bit0=1`)。
**16目盛りの偏りが入っている**(本作では `16 × 4 = 64px`)。
これは「ほぼ同じ位置にいるときに役が振動しない」ためのヒステリシス。

入れ替え: `aitick % 8 == 0` かつ 相方がCPU のとき、2人の `P_aiflag` を丸ごと交換して
`aitick++`。入替直後に `aitick` が1増えるので連続では発火しない。
**実質「およそ8打球に1回」入れ替わる。**

### 4A.5 近接時の打撃抑制 (`0x8229`)

`|P_x[me] - P_x[mate]| <= 8` かつ 相方もCPU なら打たない。
本作: `8 × 4 = 32px`。

**この 8目盛りの意味**: 同じ関数の直前に「予測着弾が自分から 20目盛り以内なら
緊急で打つ」(`0x8221` の `cmp ax, 0x14`)がある。8 はその 4割にあたる。
また 8目盛り = 画面32ドットで、**原作のキャラのコマ(32×32ドット)ちょうど1体分**。
「相方と体1個分以内に重なっていたら打たない」という意味である。

本作のキャラは 22×29px(実測)なので、32px は体 1.5個分にあたる。
コート幅を原作に合わせた以上、コート基準の `×4` を採用する。
体基準にすると原作より譲る距離が狭くなり、団子が残る。

### 4A.6 相方が近いときの退避先 (`0x8372`)

相方の方が予測着弾に近い → 自分は **ネットから16目盛り** の位置へ退く。
本作: `16 × 4 = 64px`。**相方基準ではなくネット基準**である点が重要。
現行実装は `mate.x ± 間隔` で相方を追いかけており、これが団子の直接原因。

### 4A.7 自分が取るときの先回り (`0x8376`)

`目標 = 予測着弾 - (sign(ball_vx)×2 + 2) × 向き`。
ボールの進行方向へ 2〜4目盛り 先回りする。本作: `×4` で **8〜16px**。

### 4A.8 3タッチ時 (`0x83FB`)

3回触っていたら動かない。数値なし。

### 4A.9 味方CPUの強さ (`0xB561`)

相方が人間なら `P_skill` を常に 3 (SUPER)。難易度は敵チームにのみ掛かる。

### 4B.3 反応遅延の設計を変える (ユーザー提案)

**現状の問題**: 敵が触ってから一定時間、CPUは移動もジャンプもせず**その場で固まる**。
最強で0.2秒。見た目が死んでおり、人間味がない。

**原作はそうなっていない。** 原作は2段構えで、思考が止まる時間と体が止まる時間が別:

| | 思考が止まる | 体が止まる |
|---|---|---|
| 原作 EASY | 約0.23秒 | 約0.30秒 |
| 原作 SUPER | **0秒** | 約0.07秒 |

(原作のフレームレートは未確定のため約30fpsを仮定した換算。仮定が外れれば同率でズレる)

**本作の現状はこの2つを1つに潰している。** 実装を簡単にした結果であり、設計判断ではない。

**採択する仕様**:

- 遅延が止めるのは **「新しい目標を設定し直すこと」** だけにする
- **体は動き続ける。** 直前まで向かっていた場所へは歩き続ける
- 目標の再設定が可能になるのは、従来どおり遅延の経過後

これで「気づくのが遅い」という遅延の意味は保たれ、棒立ちは消える。

### 4B.4 待機中のうろうろ (ユーザー提案。原作に無い)

**狙い**: CPUをわざと下手にするのに、いまは狙い誤差とミス抽選という
「サイコロを振ってわざと外す」仕掛けを使っている。
うろうろさせると、**外れが行動の結果として自然に発生する**。
「たまたま逆側にいた」という、見ていて理由の分かる失敗になる。

**採択する仕様**:

- 4B.1 の待機位置テーブルが決めた場所を**中心**に、左右へ小さく揺れる
- **折り返す位置は一定。端での滞在時間だけを決定論の抽選でばらけさせる**
  (向きをランダムに変えるとビクビクして見え、逆に不自然になる)
- **揺れ幅は片側27pxを上限とする**

**揺れ幅の上限が27pxである根拠**: 原作の待機位置テーブルでは、
前衛がネットから80px・後衛が240px(`×4` 換算後)で、**2人の間隔は160px**。
揺れ幅が80pxを超えると2人が重なり、いま潰そうとしている団子を再生産する。
間隔の6分の1にあたる片側27pxなら、2人が最も近づいても106px離れる。

(2026-07-25 版は「片側20px」としていたが、誤った換算率で出した間隔118pxが根拠だった。
コート幅の変更と換算率の訂正に伴い、同じ「間隔の6分の1」の考え方で引き直した)

### 4B.5 反応遅延の値 (ユーザー決定)

**最強の遅延を 0.2秒 → 0.1秒 へ短縮する。**

理由: ユーザーの実感「最強に簡単に勝ててしまう。難易度が下がって面白さが減る」。
原作の最強はほぼ0秒なので、0.1秒でもまだ原作より甘い。

**実測から出した見積り** (2026-07-25、サービスエース調査の数値から逆算):
速い球がコートを横切るのに約0.32秒。CPUの移動は3px/tick。

| 遅延 | 動ける時間 | 反応後に詰められる距離 |
|---|---|---|
| 0.20秒(現在) | 0.12秒 | 21px |
| 0.15秒 | 0.17秒 | 30px |
| **0.10秒(採択)** | **0.22秒** | **39px** |
| 0.05秒 | 0.27秒 | 48px |

実測した継ぎ目の穴は48px。0.1秒なら39pxまで詰められる。

**注意**: この見積りは**1つの場面から出したもの**であり、全体の手触りを保証しない。
遅延は数値1つで戻せるので、実プレイの結果で調整する。

弱・普通・強いの値をどうするかは未決。最強を下げた結果を見てから決める。

### 4B.6 実プレイでの確認を根拠として認める

監査で「出典なし」に分類した重力・移動速度・ジャンプ高さ・打球強さ・
ジャスト判定45%・ブレーキランク・スピードランクについて、
ユーザーが「さんざんプレイで確認してきたのが根拠。最終ポリッシュで調整する」と回答した。

**実プレイでの確認は根拠として有効**であり、このプロジェクトでは最上位の証拠と
位置づけている(メモリ `feedback-no-unsourced-benchmarks`)。
監査の分類を「出典なし」から「実プレイで確認済み・最終調整待ち」へ改める。

### 4B.7 段階を分ける理由

一度に変わる項目が10件になる。手触りが悪化したとき原因を特定できないため、
**数値で測れるものと、遊んで判断するものを分ける。**

| 段 | 中身 | 判断のしかた |
|---|---|---|
| **コート拡張** | **4B.8 (448→576)。第3段より先に入れる** | **ユーザーが遊んで判断** |
| 第3段 | 4B.1 の 1・2・3 (待機位置・退避先・前衛後衛) | 数値で測る |
| 第4段 | 4B.1 の 4・5 + 3タッチ時の移動停止 + 味方は常に最強 + 4B.2 の誤差0化 | 数値で測る |
| **第5段** | **4B.3 固まるのをやめる + 4B.4 うろうろ + 4B.5 遅延0.1秒** | **ユーザーが遊んで判断** |

**第5段の3つはセットで入れる。** うろうろで守備範囲が狭くなる分を遅延短縮が補う設計なので、
片方だけでは評価できない。ただし**遅延だけは後から単独で調整できる**ようにしておく。

4B.1 の 6 (ジャンプ発火条件) はタスク #85 として独立させる。

### 4B.8 コート幅を 448px から 576px へ広げる (2026-07-26 ユーザー決定)

**きっかけ**: 換算率の誤りを追及する過程で、原作の画面上のコート幅が
576ドットであり、**本作(448px)より広い**ことが判明した。
それまで Claude Code は「原作のコートは小さい」と誤って説明していた。

**ユーザーの判断理由**(実プレイに基づく。このプロジェクトでは最上位の根拠):

> コートを狭めるのはあり得ないし、むしろ今は狭いと感じている。だからもっと広げてほしい。
> 狭いと足の速さの特徴が死ぬ。

本作にはキャラごとのスピードランク(120/110/100/90/80)がある。
コートが狭いと誰でもどこへでも届いてしまい、**この差が体感に出ない**。
速いキャラを選ぶ意味が無くなる。コートを広げるのはこの個性を生かすためである。

**576px を選ぶ理由**: 原作の画面上のコート幅と一致し、
換算率が **ちょうど ×4** になる。以後の原作準拠作業で換算ミスが起きない。

**変更する値** (コート上の位置のみ。`576/448 = 1.2857` 倍):

| キー | 変更前 | 変更後 |
|---|---|---|
| `court_width_px` | 448 | 576 |
| `net_x_px` | 224 | 288 |
| `spawn_back_px` / `toss_zone_back_px` | 56 | 72 |
| `spawn_front_px` / `toss_zone_front_px` | 157 | 202 |
| `serve_line_px` | 24 | 31 |

**変更しない値**: 移動速度・重力・ジャンプ・リーチ・ボール半径・縦方向のすべて。

**移動速度を上げてはいけない。** 広げた分を速度の底上げで埋め戻すと、
足の速さの差を生かすという狙いが丸ごと消える。
1変数だけの変更にして、ユーザーが遊んだときに何が効いたか分かるようにする。
速度の再調整が要るかどうかは、遊んだ結果を見てから判断する。

**原作との比率について**: 原作はコート幅に対しキャラが 5.6%(576 中 32ドット)、
本作は 3.8%(576 中 22px)になる。**原作より相対的にキャラが小さい。**
これは原作忠実性より実プレイの手触りを優先した意図的な逸脱である。

### 4B.9 トスの着弾点とサーブ位置を原作へ戻す (2026-07-26 ユーザー決定)

**きっかけ**: 4B.8 のコート拡張で、Claude Code はトスの着弾点とサーブ位置を
「今の値を 576/448 倍する」と決めて実装指示を書いた。原作の値は手元にあった。

ユーザーの指摘:

> 基本原作準拠で作って、明確な変更をしたい場合は一緒に考える方針にしている
> もう勝手に決めるな、俺に決めさせろ

**原作に値があるなら原作の値を使うのが既定。** 相談が要るのは逸脱したいときだけ。
「今の値を保つ」は逸脱であり、勝手に選んでよいものではなかった。

#### 4B.9.1 トスの着弾点 (`0x571D`)

> **【2026-07-26 無効】この項の指示をそのまま実装してはいけない。**
> `toss_zone_front_px` は「自陣前へのトス」と「敵陣への返球」を兼ねており、
> 原作の値へ変えると**敵陣への返球がネットに当たってサーブが成立しなくなる**
> (実装して実測済み。`test_cpu_serve_crosses_net` が落ちた)。
> 敵陣側の切り離しを含む正しい設計は
> **`docs/superpowers/specs/2026-07-26-return-over-net-design.md`** にある。
> 自陣側の値(248 / 136)はそちらの 4.2.4 で扱う。

原作の実コード(2026-07-26 に逆アセンブルで直接確認):

```
571d  mov al, [0x115b]   ; 後ろトスなら1、前トスなら0
5721  mov cx, 0x1c       ; 28
5724  imul cx            ; 28 × フラグ
5726  add ax, 0xa        ; + 10
5729  mov bx, [bp-0xa]   ; サイド
572e  imul [bx + 0x42]   ; × 向き(+1/-1)
5732  mov cx, 0x4c       ; 76 = ネット
5735  sub cx, ax         ; 着弾 = ネット - 向き×(28×フラグ + 10)
```

ネットからのオフセットは **前トス 10目盛り / 後ろトス 38目盛り**。`×4` して本作の値。

| `rules.json` のキー | 変更前 | 変更後 | 導出 |
|---|---|---|---|
| `toss_zone_front_px` | 202 | **248** | ネット288 - 40 |
| `toss_zone_back_px` | 72 | **136** | ネット288 - 152 |

**遊びへの影響**: トスがこれまでより**ネット寄りに落ちる**。
アタッカーはネットに近い位置から打つことになり、角度が急につけられる一方、
相手のブロックとも正面からぶつかる。原作の攻撃のリズムに近づく。

#### 4B.9.2 サーブの立ち位置

原作のサーバーは壁の座標(`x=4`、壁そのもの)に立つ。本作でも壁際にする。

**ただし壁ぴったり(`serve_line_px = 0`)にはできない。**
`src/sim/simulation.gd` のサーブ照準処理はボールを
「壁からボール半径ぶん」〜「サーブ線」の範囲に収めている。
サーブ線が 0 だとこの範囲が上下逆転して成立しない
(2026-07-26、Codex が実装前に発見して停止・報告した)。

**ユーザー決定: サーバーをボール1個ぶんだけ内側に立たせる。**

| `rules.json` のキー | 変更前 | 変更後 | 導出 |
|---|---|---|---|
| `serve_line_px` | 31 | **14** | ボール半径 `ball_radius_px` と同じ |

**原作からの逸脱とその理由**: 原作は壁ぴったり。本作はボール1個ぶん内側。

#### 4B.9.3 手を出さないもの

Claude Code は 2026-07-26 にこれを不具合と決めつけて修正指示を出し、止められた。

#### 次に調べること (第4段より先)

原因の候補。**どれも未確認。着手時にまず切り分けること。**

1. **前衛/後衛の役が分かれていない。** `cpu_back_role_mask` が両方0のままなら
   2体とも前衛の値(80px)を使い、同じ場所へ向かう
2. **表を引く分岐へ到達していない。** `_cover_target()` を呼ぶ経路が
   実際には別の分岐(レシーバー退避・ブロック等)に奪われている可能性
3. **表の位置へ歩き切れていない。** 160px離れるには移動に約0.9秒かかる。
   ラリーの往復がそれより短ければ、目標へ着く前に次が来る

**切り分け方**: CPUの目標位置そのものを記録して、
「目標が表どおりか」と「実際に到達しているか」を分けて測る。
目標が正しいのに到達していないなら3、目標が既に間違っているなら1か2。

#### この測定の限界

第2段の測定以降、**コート幅・自陣トスの落下点・3打目の強制**が同時に変わっている。
**どれがどう効いたか分離できていない。**
「第3段は効いていない」と断定できる状態ではないが、「効いた」とも言えない。

**第4段へ進む前に、追っている時間と待機している時間を分けて測ること。**
待機時の距離が160px付近なら表は効いており、問題は「追いかけ方」の側にある。

ペア距離の目標は、原作の待機位置テーブル(前衛80px / 後衛240px)から
**160px** となる。2026-07-25 版の「101px」は誤った換算率から出した値なので破棄。

**3タッチ超過は解消した。** 跳べるのが1人になった効果が直接出ている。

**要監視: ジャストアタックが半減している。** 普通でも18→5。
跳べる人数が半分になったぶん芯を捉える機会が減った、という説明が付く。
**第3段・第4段を入れても戻らなければ、役割抽選の厳しさを緩める必要がある。**
その場合は「役を持たない側が打ってよい条件」を広げるのが第一候補。

32px以内が動いていないのは想定どおり。団子は第3段(4.2/4.3/4.6)の担当。
