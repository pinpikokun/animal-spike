# #85 CPUジャンプ発火ANDゲート設計

作成日: 2026-07-29

## 1. 目的

CPUが自チームの上げ球へジャンプアタックを始める条件を、原作の現在球に対する
AND判定へ絞る。届く球へ無条件に跳び続ける挙動を止め、悪い球は地上対応へ戻す。

Codexが調査、設計、実装を担当し、Claude Codeが数値、責務、検証方法を査読した。
ユーザーは両者が合意した場合の進行を承認し、両者は本設計内容へ最終合意した。

## 2. 根拠と換算

原作の `0x8824` は、ジャンプ判断時点の現在球について次をすべて要求する。

- アタッカー役である
- プレイヤーとの横距離が20内部単位未満
- ボール横速度の絶対値が5未満
- ボール縦速度の絶対値が10未満
- ボールy座標が200未満

本作へは次の厳密不等号として移す。

| 条件 | 本作の値 | 根拠 |
|---|---:|---|
| 横距離 | `< 80px` | 承認済みの原作x方向4倍換算 |
| 横速度 | `< 10px/tick` | 原作更新比と本作トス挙動から選んだ設計値 |
| 縦速度 | `< 5px/tick` | 原作更新比と本作トス挙動から選んだ設計値 |
| 高さ | `ball_y < 215px` | 原作32pxセル上端と本作28px中央の可視上端を一致させた+15換算 |

原作通常試合の実更新Hzは静的解析で確定できない。速度10と5は原作値の直接換算ではなく、
その不確実性を残した設計判断である。導出の全記録は `docs/tasks/85.md` を正本とする。

## 3. 採用方式

`SimCpu` に名前付きのピクセル閾値と `_jump_ball_ok(s, p)` を追加する。
この関数は現在球の横距離、横速度、縦速度、高さの4条件を一度に判定する。
各値は `FP.from_int()` で固定小数へ変換し、すべて厳密不等号で比較する。

ラリー攻撃ジャンプの入口に `_jump_ball_ok(s, p)` を加える。これにより、
精密会合計画 `_sweet_jump_plan()` と通常会合判定 `_jump_will_meet()` の両経路を、
条件不合格時は呼び出す前に止める。

未来接触点を各予測関数内で判定する方式は、原作の現在球判定から離れ、責務が重複する。
通常ジャンプだけを止める方式は、精密経路が条件を迂回するため採らない。

## 4. 発火条件と優先順位

対象はラリー中の自チーム非攻撃球に対する、地上からの攻撃ジャンプだけである。
既存条件に次の4条件を追加し、全条件を満たした時だけ精密計画または通常ジャンプへ進む。

1. `abs(ball_x - player_x) < 80px`
2. `abs(ball_vx) < 10px/tick`
3. `abs(ball_vy) < 5px/tick`
4. `ball_y < 215px`

サーブジャンプ、相手攻撃へのブロック、空中での打撃には適用しない。

役割は既存の承認済み仕様を維持する。アタッカー役を優先し、役持ちの相方が物理的に
会合不能な場合だけ非役持ちが代行する。代行判定で使う相方の `_jump_will_meet()` には
本ゲートを混ぜない。この関数の責務は、球質ではなく物理的な会合可能性だからである。

## 5. 毎tick再判定

ゲートは各CPU判断tickの現在球に対して再判定する。精密計画が未来の離陸を返して地上で
待っている間も例外にしない。離陸前にいずれかの条件を外れた場合は計画を保持せず中止し、
そのtickの通常位置取りへ戻る。

一度合格した計画を条件外でも保持すると、実際の発火tickにAND不合格のまま跳ぶ抜け道に
なる。永続的な計画状態と解除規則を新設することも本タスクの範囲外とする。

合格、不合格、再合格と境界を往復する球では、入力目標が切り替わる可能性を許容する。
ヒステリシスは追加しない。実測で重大な劣化が出た場合は仕様を変えず停止して相談する。

## 6. 不変条件

- 4条件はORにせず、常に同じ入口でAND評価する。
- 境界値そのものは不合格とする。
- `_jump_will_meet()` と `_sweet_jump_plan()` の弾道計算は変更しない。
- サーブ、ブロック、空中打撃の判断を変更しない。
- アタッカー優先と会合不能時の代行規則を変更しない。
- 新しい永続状態、乱数、暫定値を追加しない。

## 7. テスト先行

実装前に、次の失敗する検査を追加する。

1. `_jump_ball_ok()` の各境界
   - 横距離は `FP.from_int(80) - 1` が合格、`FP.from_int(80)` が不合格
   - 横速度は正負とも閾値直前が合格、閾値が不合格
   - 縦速度は正負とも閾値直前が合格、閾値が不合格
   - 高さは `FP.from_int(215) - 1` が合格、`FP.from_int(215)` が不合格
2. 条件内の既存会合可能球ではラリー攻撃ジャンプを維持する。
3. 4条件の各違反ではラリー攻撃ジャンプを出さない。
4. `AB_SWEET` の精密経路も条件違反を迂回しない。
5. 精密離陸待ち中に条件外へ移ったら計画移動とジャンプを中止する。
6. 合格、不合格、再合格の往復を個別tickで観測できる。
7. 役持ちが会合不能な場合の非役持ち代行を維持する。
8. サーブジャンプとブロックの既存検査を維持する。

期待値は本番の `_jump_ball_ok()` で再計算せず、固定小数の境界をテスト側で明示する。

## 8. 検証と停止条件

1. #85の対象テストを実行する。
2. 正規入口 `run_tests.ps1` を全件実行する。
3. 実装前と同じ固定seed、サーブ交互、16試合、各4000tickで再測定する。
4. 導入前後のジャンプ発火数、得点推移、ラリー長を比較する。

固定値、配列、同期ハッシュが変化した場合は回帰警報として停止し、原因を切り分ける。
ジャンプ減少が「悪い球に跳ばない」ではなく「打たずに落とす」重大な悪化へ変わった場合も、
閾値や契約を勝手に調整せず、実測を添えてユーザーとClaude Codeへ再相談する。
