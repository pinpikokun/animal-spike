# ネットを越えて相手コートへ返す打球の設計

Status: 設計。実装未着手 (2026-07-26)。

## 1. 対象

**トスサーブ(安全サーブ)と、3打目の返球。** どちらも本作では同じ処理を通る
(`hit_resolver.gd` の地上トスで、ネット方向を入力した場合)。

**対象外**: アタックサーブ(ジャンプ+下)、スパイク、ブロック。別の速度計算を使う。

## 2. 解く問題

現在この打球は「相手コートのどこに落とすか」を先に決め、そこから速度を逆算している。
**落下点を相手コート側に置いても、ネットを越えるとは限らない。**

2026-07-26 の実測: 落下点をネットの近くへ寄せたところ、CPUのサーブがネットに当たって
越えなくなった (`test_cpu_serve_crosses_net` が落ちた)。
今の数値ではたまたま成立しているだけで、**保証が無い。**

さらにこの落下点の設定は「自陣へ上げるトス」と兼用されており、
**片方を変えるともう片方が壊れる。** 上記の事故はこれが原因。

## 3. 原作はどうしているか (逆アセンブルで確認、2026-07-26)

**原作は落下点を決めていない。押したキーから速度を直接決めている** (`0x57A8`)。

```
横速度 = (ネット方向キー − 逆方向キー + 5) × 向き
縦速度 = −32 − (A+B−C)×4 + D×12 + E×8
```

A〜E はすべて「そのキーを押しているか」の 0 か 1。目標地点も相手の位置も見ていない。

**距離補正がある** (`0x581B`):

```
5809  ボールのxとネットの距離を求める
5816  40目盛りより遠いか?
581b  遠ければ 縦速度を6だけ上向きに強める
```

**打点がネットから遠いほど高く打ち上げる。** これが「必ず入る」を成立させている。

**3打目は強制** (`0x56CF`): 自チームが2回触っていたら、入力によらず必ずこの枝を通る。
サーブも同じ枝を通る(タッチ数に番兵 `0x63` が入るため)。

## 4. 採用する設計 (2026-07-26 ユーザー決定)

> 基本的にサーブ、3発目のトスは原作準拠。基本的にといったのはうちオリジナルの要素を
> 入れたいからだ。立ち位置やジャンプしていたり弾の角度や速度によって落ちる位置を変える
> 計算を入れてほしい。ただし必ず相手コートには落ちる。

### 4.1 仕組みは原作どおり、数値は本作の物理で決める

**原作の生の数値は移植しない。** 重力・ネットの高さ・ボールの大きさ・
コートに対するキャラの比率が本作と異なるため、そのまま持ってきても成立しない。

移植するのは次の3点。

1. **落下点を決めず、速度を直接決める**
2. **打点がネットから遠いほど強く打つ**(距離補正)
3. **必ず相手コートに入る**

### 4.2 落下点を変える要素 (2026-07-26 確定)

**乱数ではない。同じ状況なら必ず同じ結果になる。**

**採用する4つ**

| 要素 | 内容 |
|---|---|
| 立ち位置 | ネットからの距離。原作の距離補正(`0x581B`)を連続的にしたもの |
| ジャンプ | 打点の高さ |
| 入射 | 打つ直前のボールの速度と向き |
| **トス上手／トス下手** | 下記 4.2.1 |

**採用しない5つと理由** (2026-07-26 ユーザー決定)

| 要素 | 不採用の理由 |
|---|---|
| パワー | **パワーはアタックの指標として扱う。** あちこちに効かせると「パワーが高い＝何でも強い」になり、キャラの違いが強弱の一本道に潰れる |
| バーンアウト | 攻めを制限する仕組み。守りの返球まで弱くすると劣勢から立て直せず、罰が重すぎる |
| ジャストタイミング | 狙って強く打ったご褒美の仕組み。3打目の返球は切羽詰まった処理でご褒美を置く場面ではない |
| 打った本人の移動速度 | 前・ニュートラル・後の3方向で打ち分けの手段は足りている。混ぜると制御できない感じが増えるだけ |
| むらっけ | 「同じ状況なら同じ結果」という要件と正面から衝突する。3打目でムラが出ると理不尽 |

#### 4.2.1 トス上手／トス下手の差のつけ方

**「飛んできた球の勢いに、どれだけ振り回されるか」で差をつける。**

- **上手**: どんな球が来ても、狙ったとおりに近い返球になる
- **下手**: 速い球が来ると勢いに引っ張られて、落ちる場所がずれる

採用理由:

1. **説明が要らない。** 「上手い人はどんな球でも同じように返せる」「下手な人は来た球に振り回される」は現実のバレーの感覚そのもの
2. **新しい仕組みが要らない。** 既存の「飛んできた球の勢いが返球に乗る」処理の効き具合を、キャラごとに変えるだけ
3. **「必ず入る」を壊さない。** どちらも安全な範囲の中で動く。**下手は不利になるが自滅はしない**

不採用にした案: 「上手は奥まで運べる／下手は手前にしか落ちない」。分かりやすいが、
**下手が単に弱いだけで面白さに繋がらない。**

### 4.2.2 サーブとラリー返球で式は分けない

同じ式でよい。**サーブは自分で投げた球を打つので入射の勢いが無く、
ラリー中の返球にはある。** 勢いの有無で自然に差が出る。

結果として、**サーブは打つ側が結果を予測できる**(全部自分で決めるため)、
**ラリー中の返球は予測しきれない**(飛んできた球の勢いが混ざるため)。これは意図した設計。

ユーザーの判断: 3打目をトスで返すのは切羽詰まった場面であり、
狙って点を取りたいならアタックする。**だから3打目の返球は制御できなくてよい。**

### 4.2.3 3打目は原作どおり強制する (2026-07-26 ユーザー決定)

原作は自チームが2回触っていたら、地上打撃の入力によらず必ず相手コートへ返す
(`0x56CF`)。**本作にはこの強制が無い。** CPUが自分で「3打目だからネット方向を押そう」と
判断しているだけで、**人間が3打目に自陣へ上げると4打目になって失点する。**

原作どおり強制する。

**ジャンプして打つ場合(アタック)は別処理なので、3打目にスパイクを打つ選択肢は残る。**
バレーボールとして自然であり、原作も同じ。

### 4.2.4 自陣へ上げるトスの落下点も同時に原作へ戻す

現在 `toss_zone_front_px` が「自陣前へのトス」と「敵陣への返球」を兼ねている。
本設計で敵陣側を切り離すため、**自陣側は原作の値へ戻せるようになる。**

原作 `0x571D`: `着弾 = ネット − 向き×(28×後ろフラグ + 10)`。
ネットからのオフセットは前トス10目盛り・後ろトス38目盛り。`×4` して本作の値。

| `rules.json` のキー | 現在 | 変更後 |
|---|---|---|
| `toss_zone_front_px` | 202 | **248** (ネット288 − 40) |
| `toss_zone_back_px` | 72 | **136** (ネット288 − 152) |

**この2つは自陣側だけを指すようになる。敵陣側は本設計の速度計算が担当する。**

あわせてサーブの立ち位置も原作へ寄せる(`serve_line_px` 31 → **14**)。
原作は壁ぴったりだが、本作のサーブ照準がボールをコート内に収める前提のため、
ボール1個ぶん内側にする(2026-07-26 ユーザー決定)。

**遊びへの影響**: 自陣へのトスがこれまでよりネット寄りに落ちる。
アタッカーはネットに近い位置から打つことになる。

### 4.3 「必ず入る」の作り方

計算した速度を、**相手コートに入ることが分かっている範囲へ収める(clamp する)。**

打点によって安全な範囲が変わるため、**打点から範囲を求めてから収める。**

## 5. 実測データ (2026-07-26、`tests/zz_return_map.gd`。使い捨てのためコミットしていない)

本作の物理で、相手コートに落ちる横速度の範囲を測った。単位は px/秒。
打点の高さは床から20px(地上打ち)。

| 打点(ネットからの距離 px) | 相手コートに落ちる横速度 |
|---|---|
| 280 | 370 〜 630 |
| 240 | 320 〜 590 |
| 200 | 270 〜 540 |
| 160 | 210 〜 500 |
| 120 | 160 〜 450 |
| 80 | 110 〜 400 |
| 40 | 100 〜 360 |

**読み取れること**

- どの打点にも入る範囲が存在する。**「必ず入る」は本作の物理で成立する**
- 範囲の幅はどこでも 250 以上ある。**打ち分けの余地は広い**
- 必要な速度は**打点がネットから遠いほど上にずれる**。原作の距離補正と同じ構造が要る
- 範囲の下限はネットのすぐ向こう、上限は奥の壁ぎりぎりに落ちる。
  **相手コート全域へ打ち分けられる**

打点の高さを上げると範囲は下方向へ広がる(同じ表の高さ違いで確認済み)。

## 6.1 作業の順番 (2026-07-26 ユーザー決定)

**本設計を、CPU位置取り再設計の第4段より先にやる。**

理由: 第4段はCPUの打ち方を調整する。返球の作りが変わる前提で調整すると、
本設計が入った後にもう一度調整し直すことになる。

## 7. やってはいけないこと

- **原作の生の数値(4/5/6、−32、6 など)を本作へそのまま入れない。** 物理が違う
- **実測していない数値を仕様書へ書かない。** 5節の表以外の数値は根拠が無い
- `player_movement.gd` の左右の移動限界を変更しない。
  ネット側と壁側で扱いが違うが、ユーザーが実プレイで問題なしと判断している
- アタックサーブ・スパイク・ブロックの速度計算に手を出さない
- 乱数を入れない。決定論であること(sim層は int 演算のみ、逐次PRNG禁止)

## 8. 検証方法

1. 全打点・全高さ・全入力の組み合わせで、**相手コートに落ちることを網羅検査する**。
   1つでも外れたら不合格
2. 同じ状況で必ず同じ結果になることを検査する(決定論)
3. 既存の `test_cpu_serve_crosses_net` と `test_cpu_serve_crosses_net_right_team` が通ること
4. **3打目に地上で打つと、入力によらず必ず相手コートへ返ること**(4.2.3)
5. **3打目でもジャンプして打てばスパイクになること**(4.2.3 の但し書き)
6. トス上手と下手で、速い球を返したときの落下点に差が出ること(4.2.1)。
   **かつ両方とも相手コートに入ること**
7. 自陣へのトスが原作の位置に落ちること。左右対称であること(4.2.4)
8. 実プレイで、サーブの打ち分けが体感できるかをユーザーが判断する

## 9. 経緯 (同じ失敗を繰り返さないため)

この設計に至るまでに Claude Code が犯した誤り。

1. 自陣トスの落下点だけを原作の値へ変え、**それが敵陣側も動かすことを確認していなかった。**
   結果サーブが壊れた
2. 「3打目は自動的にネットを越える」と仕様書に書き、**根拠として無関係な行番号を添えていた。**
   実際にはそんな保証は無かった
3. 原作の生の数値を本作の物理で検算しようとした。**重力もコートも違うのだから意味が無い**
   とユーザーに指摘された
4. 「今の作りに乗る」方を推した。**原作方式なら保証がタダで手に入るという比較を
   そもそもしていなかった。** ユーザーに「今の実装を無駄にしたくないエゴでは」と
   指摘されて初めて並べて比べた
