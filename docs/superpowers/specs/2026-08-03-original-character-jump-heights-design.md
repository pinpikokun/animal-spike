# 原作8キャラのジャンプ高度と自然な共通軌道 設計

日付: 2026-08-03

状態: ユーザー指示、原作資料、実機画像4枚、試遊結果、Claude Code設計レビューを統合した実装契約。

## 1. 目的

原作8キャラのフルジャンプ到達点をPC-98版へ近づける。
同時に、プレイヤー実動とCPU予測が別々に持つジャンプ式を共通物理へ統合する。

2026-08-03の試遊で、全員を同じ25tickで頂点へ到達させる方式は、
高く跳ぶキャラほど縦速度が高度に比例して速くなり、操作感が不自然だと確認された。
ユーザーは原作動画の追加追跡より、現在のUMEを基準にした自然な速度調整を優先すると決定した。

この変更はキャラごとの条件分岐を移動処理やCPUへ足すものではない。
キャラ性能はプロフィール、軌道計算は共通物理という既存の設計原則を強める。

## 2. 根拠

### 2.1 原作コード由来の確定値

`docs/reference/original-vb22-physics.md` と
`docs/reference/original-vb22-ball-physics.md` は、原作キャラ表のジャンプ初速を
次の順で記録している。

| キャラ | 原作名 | 原作ジャンプ初速 |
|---|---|---:|
| TOME | TOME | 26 |
| HITO | HITO | 23 |
| PIYO | PIYO | 14 |
| UME | UME | 18 |
| CARBY | CARBY | 25 |
| DUO | DUO | 22 |
| SEC1 | PETIO | 10 |
| SEC2 | GATO | 20 |

原作のプレイヤー接地Yは288、ネット上端Yは258で、プレイヤー基準のネット高は30。
本作の既定値は床Y=320、ネット上端Y=275で、ネット高は45。
したがって画像で測った原作の足元高度は `45 / 30` 倍して本作座標へ移す。

### 2.2 実機画像由来の確定値

`vb2211/jump-tome.png`、`jump-hito.png`、`jump-ume.png`、`jump-caby.png` は、
ジャンプセル2の足元アンカーが最高点にある原作画面である。
スプライトの色領域と32pxセル内の足元アンカーを対応させ、接地Yとの差を測った。
ウィンドウ拡大の丸めを含むため、1px単位の厳密な原作値ではなく試遊開始値とする。

| キャラ | 原作画面の足元高度概算 | 本作の目標足元高度 |
|---|---:|---:|
| TOME | 約173 | 260px |
| HITO | 約129 | 194px |
| UME | 約73 | 110px |
| CARBY | 約157 | 236px |

### 2.3 未撮影4人の暫定値

PIYO、DUO、SEC1、SEC2には同条件の実機画像がない。
撮影済み4人では、足元高度がおおむね原作初速の二乗に比例する。
この関係を単純な整数式 `round(3 * original_speed^2 / 8)` とし、次を暫定値にする。
撮影範囲は初速18から26であり、PIYOとSEC1は範囲外への外挿になる。

| キャラ | 暫定目標足元高度 | 根拠状態 |
|---|---:|---|
| PIYO | 74px | 初速14からの暫定変換 |
| DUO | 182px | 初速22からの暫定変換 |
| SEC1 | 38px | 初速10からの暫定変換 |
| SEC2 | 150px | 初速20からの暫定変換 |

これらは原作初速そのものを確定値とし、高度だけを暫定変換値とする。
表の高度は今回の実装と回帰検査には正確な目標値だが、原作高度の検証済み絶対値ではない。
将来、同条件画像または更新周期を含む原作軌道が確定したら、プロフィール値だけを更新する。
物理コード、CPUコード、入力コードは変更しない。

## 3. 採用設計

### 3.1 性能値の正本

`src/sim/character_profile.gd` をキャラ性能値の正本とする。

- 原作8キャラはプロフィールに `jump_height_px` を明示する。
- 原作以外は既存のA-Eランク高さ表へフォールバックする。
- A-Eランクは選択画面に見せる能力区分として維持する。
- 原作8キャラの精密な足元高度を5段階へ丸めない。

公開取得関数は `jump_height_px_for_char(char_id)` とする。
この関数だけが明示値とランク値の優先順位を知る。

優先順位:

1. プロフィールに明示した `jump_height_px`
2. そのキャラのジャンプランクに対応する既存 `JUMP_HEIGHT_PX`
3. 未登録キャラの標準ランクC

### 3.2 軌道式の正本

新設する `src/sim/jump_arc.gd` を標準フルジャンプ軌道の唯一の正本とする。

責務:

- 現在のUMEの高度110px、上昇25tick、下降27tickから共通重力を求める整数式
- 目標足元高度から自然な上昇・下降時間を求める整数式
- 目標足元高度と上昇時間から離陸初速を求める整数式
- 現在の縦速度を1tick進める整数式
- 上昇中にジャンプ入力を離した場合の `vy / 2` 失速

`JumpArc` は `char_id`、キャラ名、CPU難易度、アクション種別を知らない。
入力は目標高度、現在速度、入力保持だけとし、キャラ分岐を持たない。

最小API:

- `ticks(height_px: int, rising: bool) -> int`
- `gravity(rising: bool) -> int`
- `launch_velocity(height_px: int) -> int`
- `advance_velocity(vy: int, jump_held: bool) -> int`

整数式は次の形で固定する。

- 基準高度 `reference_height = 110`
- 基準上昇時間 `reference_rise_ticks = 25`
- 基準下降時間 `reference_fall_ticks = 27`
- 上昇共通重力 `rise_gravity = FP.from_int(2 * 110) / (25 * 24)`
- 下降共通重力 `fall_gravity = FP.from_int(2 * 110) / (27 * 28)`
- 上昇時間は `rise_gravity * t * (t - 1)` が
  `FP.from_int(2 * height_px)` に最も近い整数 `t`
- 下降時間は `fall_gravity * t * (t + 1)` が
  `FP.from_int(2 * height_px)` に最も近い整数 `t`
- 誤差が等しい2候補では大きい `t` を選び、速い側へ丸めない
- 離陸初速の絶対値は
  `(FP.from_int(height_px) + rise_gravity * t * (t - 1) / 2) / (t - 1)`
- `launch_velocity` は上の絶対値へ負符号を付ける
- `advance_velocity` は上昇中の早離しなら先に `vy = vy / 2` とし、
  その結果の `vy < 0` で上昇/下降重力を選んで加える

各tickの更新順は、早離し半減、重力加算、呼び出し側の位置加算、床判定の順を変えない。
床へ到達した場合は既存どおり床Yへ固定し、縦速度を0にする。
すべて64bit整数固定小数点で計算し、平方根のfloatは使わない。

この方式では、ジャンプ時間は高度比の平方根におおむね比例する。
高いキャラはUMEより速くなるが、旧方式の高度比例ほど速くならない。
目標高度そのものは初速の補正式により±2px以内へ維持する。

### 3.3 実動とCPU予測

`player_movement.gd` は `Chars.jump_height_px(char_id)` で性能値を読み、
離陸と空中1tickを `JumpArc` に委ねる。

`sim_cpu.gd` は標準ジャンプを予測する全経路で同じ性能値と同じ `JumpArc` を使う。
対象は現在の次の4種類である。

- 地上から跳んだ場合の会合予測
- ジャスト打点への離陸計画
- すでに空中にいる選手の会合予測
- 次tickのヒット位置予測

さらに精密試行の探索時間は、そのキャラの目標高度を渡した
`JumpArc.ticks(height, true) + JumpArc.ticks(height, false)` を使う。
2026-08-03の参照棚卸しでは、`sim_cpu.gd` にある旧ヘルパー利用はこの4経路と
探索時間1箇所の合計5箇所である。実装後は `sim_cpu.gd` と `player_movement.gd` に
`_jump_height_px`、`_jump_ticks`、`_jump_gravity` の参照または定義が0件であることを検査する。

CPUは弾道を読むが、ジャンプ性能を補正しない。
人間とCPUは同じキャラなら同じ入力から同じ軌道になる。

空中打球候補は本番と同じ「入力決定、選手移動、接触」の順序で評価する。
方向キーが空中移動と打ち分けを兼ねるため、`PlayerMovement` の副作用なし予測APIで
候補入力ごとの同tick移動後座標を一括取得し、その座標から接触距離を再計算する。
移動前座標だけを使う仮想打点や、CPU都合のキャラ別高度補正は持たない。

## 4. 発火条件と状態遷移

### 4.1 標準ジャンプ開始

従来どおり、次の全条件で発火する。

- `IN_JUMP` が立っている
- 選手が接地中
- `IN_ABILITY1` が立っていない
- 構え、硬直、状態異常など既存の入力抑止を通過している

発火時:

1. キャラの目標足元高度をプロフィールから取得する。
2. `JumpArc.launch_velocity()` を `p.vy` へ設定する。
3. `p.on_ground` を0へする。

### 4.2 空中更新

1. 上昇中かつジャンプ入力を離していれば既存どおり縦速度を半減する。
2. 上昇中はUME基準の共通上昇重力、頂点以降は共通下降重力を加える。
3. 位置更新と着地判定は既存順序を維持する。

上昇から下降への状態遷移は `vy < 0` から `vy >= 0` への変化である。
新しい直列化状態は追加しない。

## 5. 変更しない境界

- 非原作キャラ4人のA-Eランクとフルジャンプ高度
- A-Eランク高さ表 `[155, 145, 135, 120, 100]`
- ジャンプ入力を早く離す可変ジャンプ
- 飛びつきレシーブの `dive_receive_hop`
- 炎上、吹き飛び、ヒップアタック、壁張り付きなどの専用縦速度
- ボール重力、打球速度、トス高度、リーチ、当たり判定
- CPUのジャンプ発火条件、難易度許可率、役割判断
- キャラ選択画面に表示するA-Eランク
- 直列化形式、状態ハッシュ、乱数消費

`cfg.jump_speed` と `cfg.hop_speed` の既存未使用整理は別課題であり、今回削除しない。

## 6. 不変条件

1. ジャンプ性能値はプロフィール以外へ複製しない。
2. 標準ジャンプの初速・重力・1tick更新式は `JumpArc` 以外へ複製しない。
3. `JumpArc` はキャラ分岐とCPU分岐を持たない。
4. 人間実動とCPU予測は同じ目標高度と同じ1tick更新式を使う。
5. 非原作キャラも自然な共通重力へ移行するが、プロフィールの目標高度は保つ。
6. 専用アクションの縦速度は標準ジャンプへ混ぜない。
7. すべての計算は64bit整数固定小数点で決定論的に行う。

## 7. 検証

### 7.1 プロフィール

- 原作8キャラが表の目標高度を返す。
- 非原作4キャラが既存ランク表の高度を返す。
- 未登録キャラがランクCへフォールバックする。
- A-Eランク表示値自体は変わらない。

### 7.2 実軌道

- フルジャンプの足元最高点が各目標値の±2px以内になる。
- UMEは変更前どおり上昇25tick、下降27tickの基準軌道になる。
- 非原作4キャラも目標高度は変更前の135±2pxを保つ。
- TOMEの総滞空時間は約80tick、CARBYは約76tick、UMEは約52tickになり、
  高度比ではなく平方根比に近い時間差になる。
- TOME、HITO、UME、CARBYの相対順が画像根拠と一致する。
- PIYO、DUO、SEC1、SEC2の相対順が原作初速と一致する。
- 暫定4人も表の実装目標値へ±2px以内で到達する。ただしこれは原作絶対値の確定を意味しない。
- 早離しジャンプは同キャラのフルジャンプより低い。

### 7.3 実動と予測

- `JumpArc` だけで積分したY列と、標準ジャンプ中のプレイヤーY列が一致する。
- CPUの地上会合、離陸計画、空中会合、次tickヒット予測が新しい共通APIを使う。
- 空中打球候補の接触予測座標が同じ入力による本番1tick後座標と一致する。
- 最大CPUの原作8キャラが左右両チーム・受け手3配置で実サーブをネットへ通す。
- `sim_cpu.gd` と `player_movement.gd` に旧ジャンプヘルパー名が残らない。
- 既存のCPU会合検査、同期検査、全件検査が通る。

## 8. 合格条件

- 原作8キャラのフルジャンプが表の目標高度へ到達する。
- 非原作キャラのフルジャンプ高度に実差分がない。
- 実動とCPU予測から旧ジャンプ式の重複がなくなる。
- 専用ホップと状態異常の軌道に実差分がない。
- `run_tests.ps1` の機能検査、同期検査、スクリプトエラー検査が通る。
- 空中候補性能ゲートは、正確な同tick打点予測を含む承認値75,000ns以内になる。
- Claude Codeの実差分レビューでCriticalとImportantが0件になる。

## 9. 停止条件

次を見つけた場合、数値をその場で補正せず停止して根拠を再確認する。

- 実機画像4人の足元アンカー解釈が誤っている証拠
- 原作初速表のキャラ対応が誤っている証拠
- 原作8キャラの専用多段ジャンプが標準ジャンプ高度を上書きする確定証拠
- 目標高度が画面外、着地不能、ネット越え不能など契約効果を壊す実測
- CPU予測と実動が同じAPIでも一致しない更新順差
- 非原作キャラ、専用ホップ、乱数列、直列化形式への意図しない差分

## 10. Claude Codeレビュー反映

Claude Codeは、性能値の正本をプロフィール、軌道式の正本を共通モジュールへ分ける案を支持した。
未撮影4人の高度を確定値と偽らないことをCriticalとして指摘したため、
本書では暫定変換値と差し替え条件を明記した。

2026-08-03の自然速度化レビューでは、UME共通重力と平方根相当の時間調整を妥当とした。
離散更新順、初速補正式、同誤差時の丸め、早離し時点、着地処理を明記するよう指摘したため、
本書3.2と4.2へ固定した。
