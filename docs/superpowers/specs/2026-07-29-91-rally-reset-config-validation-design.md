# #91 ラリー状態初期化とネット設定検査 設計書

## 1. 目的

#91 は次の二つの実バグを、既存仕様を変えずに是正する。

1. 前ラリーの移動補助状態が次ラリーへ残る。
2. ネット対戦の `SimRoot` だけが `SimConfig.valid` を検査しない。

Codex が設計・実装・検証を担当し、Claude Code が相談・レビューを担当する。
両者が本設計へ合意した後に実装する。

## 2. 根拠

`Player.push` は次の tick で横速度へ加算され、`dash` は移動速度倍率へ使われる。
`tap_dir` と `tap_tick` はダブルタップの押し始め判定と受付窓へ使われる。
いずれも位置そのものではなく、前ラリーだけに属する一時的な行動状態である。

`SimConfig` は読み込み失敗時に `valid = false` とし、呼び出し側へ検査を要求する。
表示の二経路は検査済みだが、`SimRoot.setup()` は未検査のまま state を生成する。

## 3. ラリー再開の契約

### RESET-091-001: 発火条件

`Simulation.reset_rally(s, cfg, serving_team)` が呼ばれたとき、
全選手の次の四フィールドを 0 にする。

- `tap_dir`
- `tap_tick`
- `dash`
- `push`

処理は既存の選手状態クリア列の中で行う。

### RESET-091-002: 優先順位

新ラリーの初期化を、前ラリーの入力履歴、ダッシュ残時間、吹っ飛び残時間より優先する。
初期化後の最初の tick は、四フィールドがすべて 0 の状態から始める。

### RESET-091-003: 守る不変条件

非サーバーをワープさせない既存のユーザー決定を維持する。
全選手の `x` と `y` は、この四フィールドの初期化によって変更しない。

一般の `vx`、`vy`、`hit_cooldown` は変更しない。
`hit_cooldown` は #91 が列挙する四状態とは別の打撃受付状態であり、
今回の実測症状である移動の持ち越しへ含めない。
サーバーだけを既存処理がサーブ位置へ移し、速度と cooldown を 0 にする契約も維持する。

## 4. SimRoot 設定検査の契約

### CONFIG-091-001: setup API

`SimRoot.setup()` を次と同等にする。

```gdscript
func setup(
	seed: int = 0,
	rules_path: String = SimConfig.DEFAULT_PATH
	) -> bool:
```

引数なしと `setup(0)` は、従来どおり既定ルールと seed 0 の仮初期化を表す。
`rules_path` は無効設定を実行時に検査するための副作用のないテスト継ぎ目である。

### CONFIG-091-002: 状態遷移

`cfg = SimConfig.new(rules_path)` の直後に `cfg.valid` を検査する。

- valid の場合: 新しい `SimState` を作り、従来どおり `reset_match` し、`true` を返す。
- invalid の場合: 一般理由を `push_error` し、`state = null` のまま `false` を返す。

invalid の場合は `reset_match`、ネット入力ノード生成、表示生成、peer 接続、
`SyncManager.start()` のいずれにも進まない。

### CONFIG-091-003: _ready の防御

`SimRoot._ready()` が自動初期化する場合も `setup()` の失敗後は直ちに return し、
`network_sync` グループへ追加しない。

### CONFIG-091-004: NetMatch の停止

`NetMatch._ready()` は `SimRoot.setup()` の戻り値を検査する。
失敗時は `stop_handshake()` で合意状態を失敗へ移し、理由を表示し、
ツリーへ追加前の `SimRoot` を同期解放して参照を null にし、return する。

`stop_handshake()` は `set_process(false)` を行う。
これにより設定失敗だけでなく、HUD生成前に存在する既存の早期停止経路でも、
後続フレームが未生成の `_hud` を参照しない。

## 5. 例外と範囲外

- 非サーバーの位置、速度、打撃 cooldown は変更しない。
- 設定値の補正、既定値へのフォールバック、再読み込みは行わない。
- `SimState` のフィールド、直列化順、hash 式は変更しない。
- #105 の seed 0 仮初期化、合意済み state の転写、参照同一性を変更しない。
- `NetMatch` へ設定パスを公開する本番導線は追加しない。
- ネット結合テスト用の大きな依存注入は追加しない。

## 6. テスト

### REVISION-091-001: ゴールデン停止後の実測

初回承認版の停止条件どおり、四状態クリア後に
`tests/unit/test_sync.gd::test_golden_hash_regression` だけが赤になった。
新回帰テストを含む他の 490 件は緑、SCRIPT ERROR は 0 件だった。

四状態を一つずつ切り分けた結果、固定入力で差を生んだのは
`tap_tick` のクリアだけだった。61チェックポイント中 index 0 から 8 は完全一致し、
差が出た index 9、18、47、59 は、それぞれ別のラリー再開直後の点である。
各点の次の index では旧挙動と再一致した。

| index | tick | 旧hash | 新hash |
|---:|---:|---:|---:|
| 9 | 540 | 8021131534068526972 | 8109115813815089897 |
| 18 | 1080 | 8848644209452556792 | -4094603113186017898 |
| 47 | 2820 | 579038986242948694 | -7609263877899502337 |
| 59 | 3540 | -8614871793425587985 | 3804792570101411581 |

最終 index 60 も一致した。旧ゴールデンは、消すべきダブルタップ受付窓が
ラリー直後の state hash に残る挙動を固定していた。
これは意図したバグ修正を検出した結果として、独立した意図テストを追加したうえで
合成ゴールデンを `-7934760329014079569` から `5482364282085200630` へ更新する。

### TEST-091-001: 全選手のラリー状態

四選手すべてへ、正負を含む非ゼロの `tap_dir`、`tap_tick`、`dash`、`push` を設定する。
位置を記録して `reset_rally()` を呼び、次を直接検査する。

- 四フィールドが全選手で 0
- 非サーバーの位置が維持される
- サーバー位置の既存契約が維持される

期待値を本番の初期化ヘルパーから再計算しない。

### TEST-091-002: SimRoot の無効設定拒否

既存の `res://tests/fixtures/bad_rules.json` を `setup` へ渡し、次を検査する。

- 戻り値が `false`
- `cfg.valid == false`
- `state == null`

正常な既定設定では戻り値が `true` で、既存の seed 0 初期状態を維持する。

### TEST-091-002A: ラリーをまたぐ1タップ

ダッシュ能力を持つ選手が一方向へ1回だけタップし、受付窓が残った状態で
`reset_rally()` を挟まず同じ方向へもう1回タップすると、ダッシュが発生することを
対照として先に確認する。別の同条件の選手では1回目の後に `reset_rally()` を呼び、
同じ方向への最初の1タップでダッシュが発生せず、
新しい1回目としてだけ記録されることを直接検査する。
対照でダッシュが発生しない場合、このテストは無効としてやり直す。
この検査の期待値をゴールデンhashから導出しない。

### TEST-091-003: 既存検査

正規入口 `run_tests.ps1` の全件を実行する。
次の固定検査は、ラリー境界の状態正規化により赤になる可能性を事前に警戒する。

- `tests/unit/test_refactor_characterization.gd` の固定 hash
- `tests/unit/test_sync.gd::test_golden_hash_regression`

REVISION-091-001 の1件以外の既存固定値が変わった場合は値を更新せず停止し、
どの変更がどの境界で差を生んだかを切り分ける。

RESET側とCONFIG側の変更をすべて適用した最終ツリーで `run_tests.ps1` を再実行し、
`GOLDEN_COMBINED_HASH` が `5482364282085200630` であることを再測定する。
異なる値が出た場合は値を更新せず停止し、CONFIG側の変更が
決定論へ影響した経路を切り分ける。

## 7. 合格条件

次をすべて満たした場合だけ完了とする。

1. 全選手の四状態がラリー再開で 0 になる。
2. 非サーバーの位置維持契約が変わらない。
3. `SimRoot` が無効設定から state を生成しない。
4. ネット対戦が無効設定時に同期と後続ノード生成へ進まない。
5. HUD生成前の停止後に `_process()` が動かない。
6. `setup()` の既定 seed 0 と #105 の合意初期化契約が変わらない。
7. `run_tests.ps1` が failed 0、SCRIPT ERROR 0、終了コード 0 で完了する。
8. 既存固定値は `tests/unit/test_sync.gd::GOLDEN_COMBINED_HASH` の1件のみ、
   `-7934760329014079569` から `5482364282085200630` へ更新する。
   他の固定 hash、固定配列、既知ベクタは変わらない。

## 8. 停止条件

次のいずれかを発見した場合は独断で範囲を広げず、Claude Codeと再相談する。

- 四状態以外も消さないと移動持ち越しを防げない。
- 無効設定の拒否に #105 の seed または state 転写契約の変更が必要になる。
- REVISION-091-001 で承認した1件以外の既存固定値が変わる。
- フルテストに failed または SCRIPT ERROR が出る。
- ネット失敗処理が同期開始、peer接続、未生成ノード参照へ進む。

## 9. 設計合意

Codex は本設計を採用する。
Claude Codeの初回査読条件であるHUDのnull対策、固定値停止条件、
`hit_cooldown`の範囲明示をすべて反映した。
固定値停止後の再査読条件である個別hash、独立意図テスト、更新値の限定も反映した版を
再査読し、新しい行数とSHA-256への相互合意後に実装を再開する。
