# #83 シミュレーション性能ゲート 設計書

## 1. 目的

`run_tests.ps1` の全件実行で、ロールバック再計算1コマの実時間と、
#82 が使う空中仮想打球の最重経路を常時監視する。

このゲートは同一開発機での性能退行を早期検出する。
異なる機種間で同じ速度を保証するベンチマークではない。

Codex が設計・実装・検証を担当し、Claude Code が相談・レビューを担当する。
両者が本文、行数、SHA-256へ合意した後に実装する。

## 2. 設計入力と実測

課題文の旧実測は次のとおりである。

- 1コマ: 205,566ns
- 60fpsの1フレーム: 16,666,666ns
- 8コマ巻き戻し: 予算の10.5%
- 16コマ巻き戻し: 予算の21.0%

履歴上の `tests/zz_bench_rollback.gd` は、操作対象2人のCPU入力も毎コマ作っていた。
しかし実ロールバックは保存済みの `_team_inputs` を読み、`Simulation.tick()` と
snapshot保存を繰り返す。操作対象2人の `SimCpu.decide()` は再実行しない。
`Simulation.tick()` 内で相方2人のCPU入力だけを作る。

現行コードを i5-12600K、Godot 4.6、headless でSimRoot担当範囲に合わせて再測定した。
実ロスター、全CPU `PRESET_MAX`、seed 0、試合終了を避ける勝利点、
事前生成した決定的な2チーム入力を使った。独立5プロセスで、各プロセスは
5サンプル、各2000step、各サンプル前に600step暖機した。

| 対象 | 独立5プロセスの最小値範囲 | 中央値範囲 |
|---|---:|---:|
| `Simulation.tick()` + snapshot保存 | 148,914〜152,693ns | 152,315〜155,122ns |
| `load_int_array()` | 9,046〜10,352ns | 9,335〜10,702ns |
| load + 16 × step | 2,391,839〜2,453,440ns | 2,446,453〜2,492,654ns |

旧実測205,566nsは履歴上の診断値として残すが、実ロールバックの上限根拠には使わない。
本設計の「ロールバックstep」は保存済み入力によるtickとsnapshot保存の一組とする。
SyncManagerのグループ走査、欠損入力予測、`StateBufferFrame` 生成、
`tick_finished` signal、buffer resizeは計測外であり、実step全体の下限を測るゲートである。

空中仮想打球は、3候補すべてが有効で両相手との距離を採点する固定fixtureを使い、
`SimCpu._decide_air_hit()` を7サンプル、各20,000回測定した。
独立3プロセスで最小値41,414〜42,260ns、中央値41,800〜42,479ns、
全サンプル最大43,200nsだった。
本番ゲートは実行時間を抑えるため5サンプル、各5000回とし、この特性測定より反復を減らす。

## 3. 実行場所

新規 `tests/unit/test_zz_performance.gd` を通常のユニットテストへ追加する。
`tests/run_tests.gd` のファイル名sortにより最後に実行される。

このファイルは、両ゲートをまとめた `test_` 関数を正確に1個だけ持つ。
成功時の `PERF_GATE` 出力も正確に1行だけとし、全件数は493件から494件になる。
基準機で増える全件実行時間は約4秒を見込む。

正しさは各サンプルの新品stateと暖機で保証し、実行順には依存しない。
`zz` は性能失敗を他の機能テストから分離して読みやすくする保険である。

専用subprocess、任意実行、環境変数によるskip、上限上書きは設けない。
正規入口 `run_tests.ps1` を通れば必ず性能ゲートも通る。

## 4. 共通計測規則

時刻はテスト層で `Time.get_ticks_usec()` を使い、整数だけで扱う。
各サンプルは反復ループ全体を一つの区間として計測し、
次の式で1回あたりのnsへ変換する。

```text
sample_ns = elapsed_usec * 1000 / iteration_count
```

1回ずつ時計を読む方式は採らない。
このゲートは反復区間の総コスト退行を検出し、単発のOS割込みや最大遅延は対象外とする。

5サンプルを昇順にsortし、合否には最小値、診断出力には最小値と中央値を使う。
OS割込みは遅い側へだけ混入するため、最小値を同一経路の実行能力として扱う。

## 5. ロールバックstepゲート

### PERF-083-001: 固定条件

各サンプルは次の新品worldを作る。

- `SimConfig.new()` の既定ルール
- `cfg.valid == true` の直接検査
- `Chars.ROSTER` の実ロスター
- 全選手 `SimCpu.PRESET_MAX`
- `rng = 0`、`aitick = 0`
- serving team 0
- `points_to_win = 999`

600stepを計測外で暖機し、その後2000stepを計測する。

### PERF-083-002: 1stepの内容

計測前に決定的な2チーム入力を全step分生成し、計測区間へ乱数生成を含めない。
計測する1stepは次の順である。

1. 保存済み入力で `Simulation.tick()` を1回呼ぶ
2. `{"s": state.to_int_array(), "h": state.state_hash()}` を作る

`Simulation.tick()` は各チームの相方CPU入力を内部で計算するため、
相方2選手の最強CPU思考、物理、判定とsnapshot保存を含む。

最後のsnapshotは復元計測で使い、計算が未使用にならないようにする。

### PERF-083-003: 復元

各サンプルの最後のsnapshotを使い、`load_int_array()` を2000回測定する。

実ロールバックは、状態復元1回の後に再計算stepを必要コマ数だけ行う。
したがって16コマの見積りは次の式とする。

```text
rollback16_ns = load_min_ns + 16 * step_min_ns
```

この式は `load_int_array()` 単体とSimRoot担当範囲だけを含む下限見積りである。
SyncManagerの状態読込ノード走査とbuffer resizeは含まない。

### PERF-083-004: 上限

次を両方満たすこと。

```text
step_min_ns <= 230,000
rollback16_ns <= 8,333,333
```

前者は現行独立プロセス最小値の最大152,693nsに対して約1.51倍となる
`230,000ns` の退行線である。
後者は60fps予算の50%で、描画、通信、エンジン処理へ残り半分を確保する。
step上限が成立する限り通常は後者も成立するため、後者は独立した性能線ではない。
復元処理の極端な退行を捕らえ、16コマ予算を直接表す従属バックストップとして残す。

## 6. 空中仮想打球ホットパス

### PERF-083-005: 固定fixture

`tests/unit/test_cpu_trial_shot.gd::_all_candidates_world(6)` と同じ意味の
独立fixtureを性能テスト内に作る。

- policy 2（日本語表示の「政策3」）
- 空中のattack可能選手
- 手前、中央、奥の3候補がすべて相手コートへ入り、ネットを越す
- 両相手の位置が異なり、3候補を走査して距離を採点する

計測前に `cfg.valid == true`、policyが2であること、
productionの `_air_spike_candidate()` が3本とも空でないことを直接検査する。
`_clears_net()` 単体では、既にネットを通過した有効候補と判定がずれるため使わない。
暖機後に1回、`_decide_air_hit()` の戻り値がfixtureで期待する奥候補入力と
一致することも検査し、炎打撃、sweet待ち、トスなどの早期returnへ逸れていないと固定する。
軽い地上打撃や候補1本の早期returnを同じ母集団へ混ぜない。

### PERF-083-006: 計測と上限

`SimCpu._decide_air_hit()` を1000回暖機し、5サンプル、各5000回測定する。
全戻り値を整数accumulatorへ加算し、計測後に正であることを検査する。

次を満たすこと。

```text
5,000 <= air_trial_min_ns <= 65,000
```

下限はfixture崩壊、呼び出し漏れ、計測蒸発を検出する。
上限は独立プロセス最小値の最大42,260nsに対して約1.54倍の退行線である。

## 7. 出力

成功時も次の一行を必ず出す。

```text
PERF_GATE step_min_ns=<n> step_median_ns=<n> load_min_ns=<n> load_median_ns=<n> rollback16_ns=<n> air_trial_min_ns=<n> air_trial_median_ns=<n>
```

失敗メッセージには実測値と上限値を含める。
すべてのcheckより前に `PERF_GATE` 集計行を正確に1行だけ出す。
後続checkが失敗しても2行目は出さず、失敗メッセージには `PERF_GATE` の語を含めない。

## 8. 検出能力のmutation

正式上限を変えず、コミット前の一時差分で次を順に実測する。

1. `step` 上限だけを1nsにし、性能テストが赤になること
2. 1 nominal step内でproductionのtickとsnapshot保存を2回ずつ実行し、
   約2倍の負荷で `step` 上限を超えて赤になること
3. `air_trial` 上限だけを1nsにし、性能テストが赤になること
4. 計測ループでproductionの `_decide_air_hit()` を5回に1回余分に呼び、
   約20%の負荷増では65,000ns未満で緑になること
5. 毎回1回余分に呼び、約2倍の負荷では65,000nsを超えて赤になること

一時差分はすべて戻す。productionへ空ループや計測専用分岐を追加しない。

20%のホットパス退行はこの上限で検出しない。
これは #82 実装用の余裕を先に確保するための既知の限界である。
stepも約50%未満の退行は検出しない。
このゲートは細かな速度変動ではなく、大幅なコスト増を止める初期防壁である。

## 9. #82完了後の締め直し

#82の残契約が完了した直後に、同じfixtureを5つの独立プロセスで再測定する。
各プロセスの最小値のうち最大の値へ20%を加え、1000ns単位で切り上げた値を
新しい `air_trial` 上限とする。

```text
new_limit_ns = ceil(max(process_min_ns) * 1.20 / 1000) * 1000
```

65,000nsは #82 完了までの一時上限であり、恒久上限にしない。
#82完了後はアルゴリズムが確定するため、独立プロセス最小値の最大を基準に
OSノイズと小変更の余裕20%だけを残し、現行の約54%より厳しくする。
計算値が65,000nsを超える場合は自動採用せず停止し、原因と証拠をユーザーへ報告して
承認を得る。上限を無断で緩めない。

## 10. 既知リスクと追跡

このゲートは基準機での退行検出である。
現行約153,000nsを3〜4倍すると、16コマ再計算は約7.3〜9.8msとなり、
4倍側では半フレーム予算8.33msを超え得る。

snapshot保存は旧分解計測で約88,000nsを占めており、実経路stepでも主要コストである。

低速PCで許容する巻き戻し数の実機確定とsnapshot最適化は #83 へ混ぜない。
追跡を失わないため `docs/tasks/111.md` を追加し、P1残件へ登録する。

## 13. 合格条件

次をすべて満たした場合だけ完了とする。

1. 正規全件入口で性能ゲートが必ず動く。
2. rollback stepと16コマ再計算が承認上限以内である。
3. 3候補空中仮想打球が承認上下限以内である。
4. stepが1nsと約2倍で赤、air trialが1nsで赤、約20%で緑、約2倍で赤になる。
5. 独立5回の全スイートがすべて緑になる。
6. 実行順を変えても既存固定値とゲート結果が成立する。
7. productionコードと既存固定値を変更しない。
8. 低速PCとsnapshotの残リスクを #111 で追跡する。

## 14. 停止条件

次のいずれかで値を緩めず停止し、Claude Codeと再相談する。

- 基準実装が承認上限を超える
- 3候補fixtureがpolicy 2または全候補有効を満たさない
- stepまたはair trialの1ns・約2倍mutationで赤にならない
- 約20%mutationで上限を超える
- 5回検証の1回でも性能ゲートが赤になる
- 実行順変更で固定値または性能合否が変わる
- 性能テスト以外の既存テスト、固定値、production変更が必要になる

## 15. 設計合意

Codex は本設計を採用する。
Claude Codeは、全体平均だけでは #82 を希釈する問題に加え、
実ロールバックでは操作対象2人のCPU入力を再計算しないことを指摘した。
CodexはSimRoot担当範囲を再測定し、3候補fixtureの直測定、上下限、両ゲートのmutation、
#82後の上限締め直し、実行順の位置づけを本文へ固定した。
Claude Codeは全指摘の反映後にP0/P1なしを確認し、
`CLAUDE_OK_UNCONDITIONAL: #83設計を実装へ進めてよい` と無条件承認した。
