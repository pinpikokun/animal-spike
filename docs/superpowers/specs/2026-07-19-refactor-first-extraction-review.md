# 挙動を変えない最初のリファクタリング: Claude Code設計レビュー

日付: 2026-07-19
状態: 提案(実装未着手)。Codex案(2026-07-19-ability-traits-toss-refactor-design.md
「Refactoring strategy」節)への対案と反対意見を含む。

## 前提認識

- simulation.gd は現在1077行。最大の複雑源は `_apply_hit`(約210行)で、
  ジャスト判定・慣性・支配権切替・制御喪失(mangle)・地上/空中トス表・
  スパイク・ばらつき・タッチ数までを1関数で処理している。
- 作業ツリーには**挙動変更を含む未コミットdiff(+454行)**がある
  (能動ブロック、ジャンプ高度式、トス低軌道失敗、サーブ慣性ゼロ、
  ばらつきのアタック限定化、選択画面の能力表示)。
- 過去に simulation↔sim_cpu の循環preload問題を踏み、
  sim_cpu側に帽子定数のミラー+ガーディアンテストという負債が既にある。

## 結論(要約)

1. Codexの「段階式・挙動不変が先・特性テストが先」という骨格には**全面同意**。
2. ただし**8モジュール分割は1077行に対して過剰**。最初の分離は3つに絞る:
   `hit_resolver.gd` / `ball_physics.gd` / `player_movement.gd`。
3. **リファクタ開始前に、未コミットの挙動変更を先に確定させる**こと。
   これをやらないと「挙動不変の証明」が原理的に不可能になる(最重要の反対点)。
4. 分離は「**逐語移動**(コードを一切書き換えずに移す)」を規律とし、
   ゴールデンハッシュ定数を**1ビットも動かさない**ことで挙動不変を証明する。

## ステップ0(必須の前提): 汚れたツリーの確定

現在のdiffは挙動変更とテスト更新が混在した未コミット状態にある。
リファクタリングの合格判定は「ハッシュ不変」だが、**基準となるハッシュが
未確定のツリーでは判定基準そのものが存在しない**。よって:

- 0-1. 現diffを意味単位でコミットに分割して確定する
  (能動ブロック+CPUブロック入力 / ジャンプ高度式 / トス低軌道失敗+
  ばらつき限定化 / サーブ補正 / 選択画面表示 / 仕様書)。
- 0-2. 全テストを緑にし、test_sync のゴールデンを最終値で確定する。
- 0-3. ここで得たコミットを「リファクタ基準点」としてタグを打つ
  (例: `pre-extract-refactor`)。

Codex案はこの手順を明文化していない。**ここが最大の危険点**であり、
省略すると「抽出でズレたのか、混在していた挙動変更でズレたのか」を
永遠に切り分けられなくなる。

## 最初に分離する責務(3モジュール案)

分離順は「依存が葉に近いものから」。すべて static func のみ・状態を持たない。

### 1. ball_physics.gd(最初。最も葉に近い)

- 移すもの: `_step_ball` `_ball_vs_net` `_ball_vs_block` `_step_ball_loose`
  と関連定数(LOOSE_BOUNCE_PCT等)。
- 公開IF(現シグネチャを維持):
  - `step_ball(s, cfg, inputs) -> void`
  - `step_ball_loose(s, cfg) -> void`
- preloadは FP / sim_state(定数) / chars / sim_input のみ(葉規律)。

### 2. hit_resolver.gd(本丸。最大の複雑源)

- 移すもの: `_resolve_hit` `_apply_hit` `_is_active_block` `_scatter`
  とヒット系定数(MANGLE_AIM_PCT, TOSS_AIM_SHIFT_PX, KNOCKBACK_PX,
  PUSH_*, FLINCH_TICKS 等)。
- 公開IF:
  - `resolve_hits(s, inputs, cfg) -> void`(現 `_resolve_hit` を改名公開)
  - `scatter(s, actor, salt) -> int`(CPU/テストからも参照可能に)
  - 定数を公開(下記「ミラー定数の解消」参照)。
- **副次効果(この分離の最大の実利)**: sim_cpu が hit_resolver を
  preloadできる(循環しない)ため、sim_cpu内の帽子・物理ミラー定数と
  ガーディアンテストを**本物の参照に置換して削除**できる。
  ※ミラー解消自体はステップ3の後に独立コミットで行う(逐語移動と混ぜない)。

### 3. player_movement.gd

- 移すもの: `_step_player` とジャンプ/重さ/ダッシュ/push系定数。
- 公開IF: `step_player(p, input, cfg, team) -> void`。

### 今回は分離しないもの(Codex案への反対)

- `action_intent.gd`: 意図分類は現状 `_apply_hit` 内の分岐と速度決定が
  一体で、利用者が1箇所しかない。**独立ファイルにする根拠が薄い**。
  代わりに hit_resolver 内の純関数
  `classify(p, input, s, d2) -> int`(意図enumを返す)として抽出し、
  特性テストの土台にする。ファイル分割は消費者が2つ以上になってから。
- `serve_resolver.gd` / `status_resolver.gd` / `character_profile.gd`:
  サーブは約60行、ガード/スタンはヒット処理と密結合、プロファイルは
  chars.gd が既にその役割。**行数が問題になってから引く(YAGNI)**。
  A-E実装時に必要になった時点で追加抽出すればよい。分割自体が目的化した
  8ファイル構成は、GDScriptのpreloadグラフを複雑にし、循環と
  ミラー定数の再発リスクを増やすだけ。

## 決定論と同期ハッシュを維持する方法

1. **逐語移動の規律**: 抽出は「切り取って貼る」のみ。改名・演算順序の変更・
   `/`の位置変更・変数の畳み込み・matchへの書き換えを**同一コミットで禁止**。
   整数除算は非結合なので、見た目の等価変形が値を変える。
2. **ハッシュ凍結**: ステップ1〜3の間、test_sync のゴールデン定数は
   変更禁止(変更が必要になった時点でそのコミットは失格=挙動が変わった証拠)。
3. **葉preload規律**: 新モジュールは FP/chars/sim_input/sim_state 以外を
   preloadしない。simulation→新モジュールの一方向依存のみ許す。
   sim_cpu→新モジュールは許す(これがミラー定数解消の鍵)。
4. **乱数の互換**: `_scatter` のハッシュ式・salt値・呼び出し順を移動後も
   完全一致させる。salt一覧を hit_resolver に定数表として集約し、
   「同一saltの用途重複禁止」をコメントで明文化する
   (現状、ブロックばらつきとトス低軌道rollが salt=17 を共用している。
   同tick同actorで相関し得るため、挙動確定後の別コミットで採番し直すべき)。
5. **状態フィールド不変**: 抽出でsim_stateのフィールド・直列化順序は触らない。

## 先に追加する特性テスト(characterization tests)

既存213+本に加え、抽出前に以下を「現挙動のスナップショット」として固定する。

1. **意図分類表テスト**: (地上/空中)×(上/下/横/無)×(リーチ縁/近接)の
   全組み合わせ→どの分岐に入るか(hit_kind・vyの符号・sweet有無)を表で固定。
2. **出力速度スナップショット**: 固定フィクスチャ格子
   (入射: 静止/緩球/強球/パワーボール × ジャスト/芯外し × 主要入力)に対する
   ball_vx/ball_vy の**整数値そのもの**を期待値として記録。
   逐語移動の失敗はここで即検出される。
3. **衝突順序テスト**: 同tickでのヒット→ボール移動→ネット→ブロックの
   処理順を、境界配置のフィクスチャで固定。
4. **乱数ストリームテスト**: 固定(tick, actor, salt)に対する `_scatter` の
   返り値列を定数で固定(移動後のずれを即検出)。
5. **シナリオ・ゴールデン第2弾**: 現在の60秒CPUゴールデンは、ダッシュ
   (ロスター未所持)や気絶壁飛びを**通らない可能性が高い**。スクリプト入力の
   リプレイで「ジャスト成立→mangle→ブロック→気絶壁飛び→帽子投げ」を
   確実に踏む短いシナリオを作り、その合成ハッシュを第2ゴールデンとして追加。
   カバレッジ外の逐語移動ミスを塞ぐ。

## 変更の分割単位と順序

| # | コミット | 合格条件 |
|---|---|---|
| 0 | 未コミットdiffの意味別確定+タグ | 全テスト緑・ゴールデン確定 |
| 1 | 特性テスト追加(プロダクションコード変更なし) | 全テスト緑・ハッシュ不変 |
| 2 | ball_physics.gd 抽出(逐語移動) | 同上 |
| 3 | hit_resolver.gd 抽出(逐語移動) | 同上 |
| 4 | player_movement.gd 抽出(逐語移動) | 同上 |
| 5 | sim_cpuのミラー定数を本物参照へ置換・ガーディアン簡素化 | 同上 |
| 6 | (挙動確定後の別作業) salt採番の整理 | ゴールデン意図的更新1回 |

各コミットは pre-commit フックの全テストを通し、`git diff --check` を通す。
1コミット=1抽出。複数モジュールの同時移動は禁止。

## Codex案への反対意見・危険性(忖度なし)

1. **開始前のツリー確定が計画に無い(最重要)**。挙動変更が未コミットのまま
   「挙動不変リファクタ」を始めると、不変の証明が不可能。ステップ0を必須とせよ。
2. **8モジュールは過剰分割**。1077行に8ファイルは1ファイル平均130行。
   GDScriptではファイル境界=preload境界=循環リスクであり、境界を増やすほど
   「sim_cpuのミラー定数」型の負債が再発しやすい。まず3つ。残りは
   A-E実装が実際に必要とした時点で引く。
3. **action_intentの独立ファイル化は時期尚早**。消費者1つの抽象化は
   間接参照を増やすだけ。関数抽出で同じテスト容易性が得られる。
4. **「テスト・ハッシュ不変」の運用定義が曖昧**。逐語移動の規律
   (改名禁止・演算順序不変・saltと呼び出し順不変)まで落とさないと、
   善意の「ついで整理」が整数除算の順序を変えてハッシュを壊す。
5. **現ゴールデンのカバレッジ過信**。60秒CPUラリーはダッシュ・気絶壁飛び・
   帽子投げを踏まない可能性がある。シナリオ・ゴールデン第2弾を先に足すべき。
6. (refactor外だが記録) 未コミット実装の懸念2点:
   - salt=17 がブロックばらつきとトス低軌道rollで重複している。
   - 能動ブロックがIN_ACTION+ネット方向を先取りするため、ネット際60px圏では
     「入射球への前トス」入力がブロックに化けて打てない。仕様通りかは
     ユーザーの手触り確認が必要。

## 合意している点(明記)

- 段階式(特性テスト→挙動不変抽出→データモデル→挙動実装→旧コード削除)。
- 全面書き直しの禁止。モノリスへの新規則直積みの禁止。
- CPUと人間が同じ関数・同じ物理を使う方向。
- 最終的なモジュール像(8責務)は**到達点としては妥当**。争点は「最初の一歩で
  いくつ切るか」だけであり、3→残りは需要駆動で増やせば同じ地形に到達する。
