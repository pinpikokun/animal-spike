# キャラクター拡張アーキテクチャ設計（キャラ独立+物理コア1つ+4層構造）

日付: 2026-07-17
状態: ユーザーとの設計問答で合意した内容の清書。実装は本スペックのレビュー承認後、writing-plansで計画化してから行う。

## 0. 背景と目的

キャラクターを8体前後+増員していくにあたり、「キャラを追加したら他キャラの挙動に引っ張られる」事態を構造的に防ぐ。あわせて、アイテム（帽子以外も追加予定）、設置物、見た目の状態変化（帽子脱げ・パワーアップ）、固有アクション（ワープ・飛行・電気等）、キャラごとのステータス差、MOD対応の器をこの設計で確保する。

多エージェント検討会（設計3案+審査3+統合、2026-07-17実施）の結論と、ユーザーの方針を統合したもの。

## 1. 設計原則（憲法）

1. **1キャラは独立**（ユーザー方針）。1キャラ=1フォルダ。キャラの個性（数値・固有技・表示演出）は自キャラのフォルダ内で完結し、他キャラに影響しない。同種の処理がキャラ間で重複してもよい。
2. **物理コアは1つ**。ボール物理・当たり判定の解決・ルール進行・共通動作の実装はコピーしない。理由: ロールバックネット対戦でのデシンク防止。コピーされた物理の微妙な差異はデシンクの温床であり、1人開発で追跡不能。
3. 既存の決定論憲法を維持: sim層は64bit int演算のみ、全状態は直列化・ハッシュ照合対象、CPU入力生成も決定論。
4. **オーバーライド優先**（ユーザー方針）: 基本挙動はデフォルトとして存在し、キャラは上書きしたい箇所だけ上書きする。MODはキャラフォルダ形式での追加を将来の正式ルートとする。

## 2. 4層構造

### 第1層: 共通動作（実装1つ、全キャラ共有）

バレーのルールに直結する動作。実装は物理コアに1つだけ。

標準アクション一覧（=キャラが用意すべきスプライトのアクション名一覧）:

| アクション名 | 内容 | 備考 |
|---|---|---|
| idle | 立ち | 最低限これか歩きが必須 |
| run | 歩き/走り | |
| jump | ジャンプ | |
| attack | 空中アタック(スパイク鋭角/緩角共用) | |
| toss | 真上トス | |
| toss_fwd | 前トス | |
| crouch | しゃがみ/レシーブ姿勢 | |
| brake | 急ブレーキ | |
| stun | スタン(気絶) | |
| hurt | 被弾しりもち | |
| victory | 勝利ポーズ | |

ジャストアタック/ジャストレシーブ/ジャストトス、ブロック、サーブ（構え→トス→打撃）は上記アクションの状態遷移として共通コアが処理する（専用スプライトは任意、無ければ代役ルール）。

固有技のスプライト（帽子投げ・ヒップアタック・壁張り付き・ワープ等）は、その技を持つキャラだけが技モジュール指定のアクション名で用意する（無ければ代役ルール）。

### 第2層: キャラステータス（キャラ定義の数値、共通コードが読む）

全てint（%は100=標準）。共通コードは計算時にこの数値を掛ける。

- 移動速度% / ジャンプ力% / 重さ%（落下・着地演出・砂煙量に影響）
- 耐久値(guard_max) / 急ブレーキ滑走距離%
- 通常アタック威力% / ジャストアタック報酬%（威力・演出の倍率）
- ジャスト窓の広さ%（0=そのキャラはジャスト不可、も数値で表現可能）
- 当たり判定: 共通リーチ%（横・縦）+ アクション別部位判定（後述）

**ジャスト系は全キャラ標準装備**（有無のキャラ分けはしない）。理由: ジャストはプレイヤーの腕前の表現であり、ジャストレシーブ回復・ジャストトス回復の経済システムに組み込まれているため、持たないキャラは構造的不利かつ操作の深みを失う。個性は窓の広さと報酬倍率で出す（例: パワー型=機動力70%・アタック威力130%・ジャスト報酬150%）。

### 第3層: 固有技=アクティブ能力（技モジュール、付け外し自由）

- 技1つ=独立した技モジュール（例: ability_hat.gd 帽子投げ / ability_cling.gd 壁張り付き / ability_warp.gd 短距離ワープ / ability_dash.gd 前2回ダッシュ / ability_hover.gd 空中浮遊）
- キャラ定義に技名を列挙するだけで付け外し。同じ技を複数キャラが持ってよい（実装は共有、パラメータはキャラ定義から渡す=ワープ距離の個体差等）
- **壁張り付きはマリオ固有ではなく付け外し式の固有技とする**（ユーザー決定。サル・リス等も持てる。現状の「全キャラ使える」実装漏れはこの移行で修正）
- ヒップアタックは帽子所持への相乗りをやめ、独立した技とする
- 技モジュールは本体プロジェクト内のコード。実行時外部読み込みはしない（決定論・対戦互換のため）。新技の追加=技ファイル1個の追加で、他キャラ・他技に影響しない

起動方法は2系統: (a) 固有技ボタン（後述の技スロット）、(b) コマンド入力（入力履歴バッファで判定。前2回ダッシュ、必殺技と共用の部品）

### 第4層: パッシブ能力（入力なしで発動）

共通コアに差し込みポイントを定義し、キャラ定義で列挙して付け外し:

- 落下速度補正（鳥系のふわふわ落下等）/ 着地時フック / 被弾時フック（ダメージカット等）/ 反転時フック（滑らない等）

パッシブは制御感を奪いやすい（ブロック暴発の前例）ため、採用は1個ずつ実物の手触り確認を経る。

## 3. 入力設計

- ネット対戦で送る入力ビット列に**技スロットを複数予約**する: 技1〜技4（現在使用は技1=Dのみ。ビット予約はタダ同然、後からの追加はネット互換を壊すため最初に確保）
- 現在の IN_HAT_THROW は **IN_ABILITY1（固有技ボタン1）に改名**。「押されたら何が起きるか」はキャラ定義が決める（マリオ=帽子投げ、忍者ネコ=ワープ等）
- 物理キー→スロットの割り当て（キーバインド）は表示層の設定で自由。ユーザー/MODが変更可、対戦相手と違ってよい
- **入力履歴バッファ**をsim層に追加（ロールバック時は履歴も巻き戻す）。ダッシュの2回入力とコマンド必殺技の共用部品

## 4. 当たり判定

- 判定はスプライトと完全分離（simは画像を読まない。絵の差し替えで判定・対戦は不変=MOD安全）
- 共通判定: 現行の楕円（横広・縦狭）にキャラ%補正
- **アクション別部位判定**: キャラ定義に「アクション名→判定中心オフセット+サイズ」の表を持てる（例: 大型キャラのattackは手元に小さく集中）。指定なしは共通判定。向きで自動反転。CPU AIも同じ表を読む
- 開発用の**判定可視化デバッグ表示**を用意し、絵と判定のズレはユーザーの目視で詰める

## 5. エンティティ枠（アイテム・飛び道具・設置物）【正式採用】

- 現行の帽子（cap_* のstate直書きシングルトン）は**アイテム2個目で破綻**する（検討会全員一致の所見）。固定枠のエンティティ配列に移行する
- エンティティ=種別(kind)/フェーズ/位置/速度/所有者/チーム/寿命/予備欄を持つ固定スロット（例: 8枠、全欄常時直列化=ハッシュ・ロールバック安全）
- 飛び道具（帽子・電気弾・投げ武器）も**設置物**（自陣のバネ、敵陣のトラップ等、ユーザー将来構想）も同じ枠。違いは属性値（動くか・寿命・作用対象チーム）
- 種別ごとの挙動は kind別モジュール(ent_cap.gd等)に分離。ボールを弾く/プレイヤーに作用する等の共通衝突は属性テーブルで処理
- 生成は先頭空きスロットへの線形走査（決定論）。満杯時は生成失敗（安全側）

## 6. 見た目（表示層）

- **キャラフォルダ**: `characters/<name>/` に定義（ステータス・技・姿ごとの性能表）+ 表示定義（コマ割り表・セル寸法・足元基準・演出個性）+ スプライト一式
- **コマ割り表**: アクション名→{シート, コマ番号列, 保持tick列, ループ}。コマ数は自由（歩き2コマも10コマも可）。セル寸法・基準点もキャラごと
- **シート形式は両対応**: アクション別ファイル（現行マリオ式）と全部入り1枚シート（AI生成ツール出力形式、行×列グリッド指定を追加）
- **代役ルール**: スプライトが無いアクションは定義済みの連鎖で自動代用（attack→jump→run→idle等）。歩きか立ち1枚あればキャラ成立（パンダ方式の公式化）。代役発生は開発ログに警告
- **姿(form)の変化**: simにform値（int、正式状態=ロールバック対象）。性能が変わる変身はキャラ定義の「姿ごとの性能表」を参照。表示は「キャラ×form→スプライト一式」の対応表（帽子脱げが第1号、パワーアップも同経路）
- **共通演出**（着地スカッシュ&ストレッチ・砂煙・画面揺れ等）: 既定=全キャラON、強さはキャラ定義の数値（既定は重さから自動導出）、OFF指定も可
- 表示層はキャラごとのGDScriptクラスで自由に書いてよい（決定論の外。個性フラグが増殖したらクラス化へ移行）

## 7. CPU AI

- 「**できるか**（キャラ定義の技リスト）AND **やりたがるか**（CPUプロファイルのAB_ビット）」の二段ゲート
- 既存技の組み合わせキャラの追加なら sim_cpu.gd は0行変更。新技をAIに使わせる時だけ、判断関数1個+ゲート1行を追加
- CPUプリセットはキャラ非依存のまま（全技ビットを立てておき、実際に使えるかはキャラ定義が決める）

## 8. キャラ定義の形式とキャラID

- プレイヤー状態に **char_id（キャラ識別子）を追加**する（検討会所見: 「slot番号=キャラ」の暗黙対応こそ最も剥がしにくい負債。直列化形式は再生成可能な後ドアだが、キャラID概念の欠如は先送りするほど高くつく）
- キャラ定義の置き場所: 当面はGDScript定数（型チェック・grepが効く、1人開発の速度優先）。**MOD開放の段階でJSONローダに差し替え**（その際GodotのJSONは数値をfloatで返すため、int確定検証を必須とする。rules.jsonに前例あり）
- 表示層3ファイル（sprite_factory/game_view/score_ui）のslot=キャラのハードコードは、char_id経由の辞書参照に置換して解消

## 9. 段階移行計画（各段で181テストを緑に保つ）

1. char_id導入+現行と同値のキャラ定義（挙動不変を確認）
2. 固有技のビットゲート化（帽子/ヒップ/壁張り付きの独立化。壁張り付きの固有技化は仕様変更としてゴールデンハッシュ更新）
3. 技スロット予約+IN_ABILITY1改名（ネットプロトコル確定はM2フェーズ2前に）
4. 表示層のchar_id辞書化+コマ割り表のデータ化+代役ルール
5. エンティティ枠への帽子移植（ゴールデン再生成は1コミットに束ねて1回）
6. ステータス%の適用（全キャラ100で開始=挙動不変。裸のcfg参照を禁じるgrep番人テストを併設）
7. 入力履歴バッファ+ダッシュ（最初のコマンド技として）

## 10. 却下した選択肢

- **キャラごとに物理コアをコピーして完全独立**: デシンクの温床、1人開発で追跡不能（ユーザーと合意済み: 独立はキャラ層まで、コアは1つ）
- **JSON内に挙動を書くDSL**: 決定論intの世界でDSLはテスト地獄。新しい技は必ずコードで書く
- **ジャストアタックのキャラ固有化**: 経済システムからの締め出しと操作の平板化を招く。窓0%の数値表現で事実上の固有化は後からでも可能（可逆）
- **MODによる入力ビットの自由追加**: ネット互換を壊す。スロット予約制で対応

## 11. ユーザー確認済み事項

- 壁張り付き=付け外し式の固有技（マリオ・サル・リス等が持つ）
- ジャスト系=全キャラ標準+窓/報酬はキャラ数値
- パワー型の設計例=機動力低・アタック威力/ジャスト報酬高、を数値で表現
- 固有技ボタンのスロット式（D=技1、キーバインド自由）
- 設置物・武器アイテムの将来対応（エンティティ枠の正式採用）
