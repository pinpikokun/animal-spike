# #82 仮想打球テスト 残契約設計

## 1. 目的

空中ラリーで完成済みの実速度3候補と4政策をジャンプサーブへ共通化し、
仮想打球で安全性を判断できるようになった後も残っている120px制限を撤去する。

同時に、ユーザー決定済みの幅格子は仕組みだけを実装する。
難易度ごとの値は #84 まで決めず、現行productionは全員 `k = 0` とする。

Codexが設計、実装、検証を担当し、Claude Codeが相談、設計査読、実装レビューを担当する。
ユーザーは両者が合意した場合の進行を承認済みである。

## 2. 基準状態

基準は #83完了後の `main` とする。

- `7602485` で空中ラリーの実速度3候補、4政策、空中トス、ネット通過済み接触は完成済み
- `test_zz_performance.gd` はpolicy 2（政策3）の3候補最重経路を常時測定
- 正規入口は494 tests, 0 failed、SCRIPT ERROR 0
- production作業ツリーはclean

## 3. 仕様の優先順位

次の順で適用する。

1. `docs/tasks/82.md` に記録されたユーザー決定

特に、ブロック側120px撤去と幅格子の仕組みは生きている判断として扱う。

### 4.2 対象外

## 5. 現在の不成立

### GAP-082-001: ジャンプサーブが③奥固定

`_decide_serve()` は空中接触時に `ACTION | DOWN | fwd` を直接返す。
このためジャンプサーブは `_pick_air_shot()` を通らず、候補は③奥だけ、政策は0回である。

### GAP-082-002: 120px制限が2箇所に残る

- `_decide_air_hit()`: 自分がネットから120px未満でなければアタックしない
- `_decide_block()`: 相手アタッカーがネットから120px以内でなければ反応しない

両者は対の代用品であり、片方だけを撤去してはならない。

### GAP-082-003: 幅格子が未実装

現行 `_air_spike_candidate()` は実速度の中心1点だけを調べる。
これは `k = 0` の挙動として正しいが、#84が非ゼロ値を決めた時に使う仕組みがない。

### GAP-082-004: ブロック契約の検査が消滅

旧契約の次の2件は現在のテストに存在しない。

- 120px超の相手アタッカーにもブロックへ反応する
- ネット到着後も既存の役割と優先順位が変わらない

撤去を検出できる既存テストはないため、実装と同時に直接検査を復活させる。

## 6. 幅格子

### GRID-082-001: 定数

`sim_cpu.gd` に次を置く。

```gdscript
const TRIAL_BAND_STEP_PCT := 10
const TRIAL_BAND_K_MAX := 3
const TRIAL_BAND_CURRENT_STEPS := 0
```

`TRIAL_BAND_CURRENT_STEPS` は全production呼び出しが共有する。
プロファイル、キャラクター、rules.jsonから値を読まない。

非ゼロ値の導入は #84 の新設計と #83 の再設計、再測定を必須とする。

既存6引数呼び出しを壊さないため、`_air_spike_candidate()` の格子段数は
末尾の既定引数 `k = TRIAL_BAND_CURRENT_STEPS` として追加する。
productionと既存 #83 fixtureは引数省略で現在値0を使い、
幅機能テストだけが明示的に非ゼロを渡す。

### GRID-082-002: 中心速度

中心は `HitResolver.preview_air_spike_velocity()` が返す正確な実打球速度とする。
固定倍率は復活させない。

```text
step_x = abs(actual_vx) * 10 / 100
step_y = abs(actual_vy) * 10 / 100
trial_vx = actual_vx + sign(actual_vx) * ix * step_x
trial_vy = actual_vy + iy * step_y
```

整数除算は非負値の切り捨てとする。
`k = 0` は `(ix, iy) = (0, 0)` の1点で、現行の正確速度と完全一致する。

### GRID-082-003: 十字と走査順

`iy` を `-k` から `+k`、その内側で `ix` を `-k` から `+k` の順に走査する。
`ix == 0` または `iy == 0` の点だけを評価する。

`actual_vx == 0` の場合は `ix != 0` を除外する。
速度成分の歩幅が整数丸めで0になった場合も、仕様上の格子点は削除しない。

有効範囲は `0 <= k <= TRIAL_BAND_K_MAX` とする。
範囲外なら候補を無効として返し、黙ってclampしない。

点数は相異なる速度の数ではなく、評価する論理格子座標の数を指す。
歩幅が0へ丸まって同じ速度が複数回現れても座標点を重複排除しない。
非ゼロの `actual_vx` では `4k + 1` 点、`actual_vx == 0` では横点を除くため
`2k + 1` 点になる。

### GRID-082-004: 有効点とCPUが信じる予測

各格子点は既存と同じ条件で評価する。

1. `_land_x_from(..., max_bounce = 3)` の落下点が相手コート側
2. 打点が自陣側なら `_clears_net()` が真
3. 打点が既に相手側ならネット通過済みとして2を省略

有効点のうちマンハッタン距離 `abs(ix) + abs(iy)` が最小の点を、CPUが信じる予測にする。
同距離ならGRID-082-003の走査順で先に見つかった点を使う。

候補の戻り値は現行と同じ `[actual_input, believed_land_x]` の2要素配列を維持する。
呼び出し側は要素0を採用入力、要素1を政策3の得点用着地点として読み続ける。
実際に打つ入力は中心速度と同じ3方向のままで、幅の予測速度を実球へ代入しない。
非ゼロkでは、有効だと信じて採用した実球がネットへ当たることを意図したミスとして許す。

### GRID-082-005: 計算量

十字の点数は `4k + 1`、最大13点である。
政策3は3候補を調べるため、構造上限は39点とする。

この13点と39点は `actual_vx != 0` の論理格子座標上限である。
相異なる速度数を数える契約ではない。

productionは `k = 0` なので、現在到達する上限は3候補3点のままである。
productionへ計測専用カウンタは追加しない。

## 7. ジャンプサーブ共通化

### SERVE-082-001: 対象条件

次をすべて満たす既存枝だけを変更する。

- `phase == PHASE_SERVE`
- `serve_tossed == 1`
- サーバー本人
- `attack_serve == true`
- プレイヤーが空中
- ボールが既存接触楕円内

地上通常サーブと、空中接触へ到達するまでの移動・ジャンプ計画は変更しない。

### SERVE-082-002: 共通選択

現在の③奥固定入力を次の意味へ置き換える。

```gdscript
return _pick_air_shot(
    s, idx, cfg, s.serving_team, true, d2,
    TRIAL_BAND_CURRENT_STEPS)
```

実際のシグネチャは重複を避けて整理してよいが、サーブ専用の候補表、政策、速度式を作らない。

`preview_air_spike_velocity()` は `serve_strike` を読み、サーブ時の慣性0を含む正確速度を返す。
3候補、政策写像、有効判定、政策3の得点式はラリーと同じ関数を使う。

実装前の読み取り専用診断で、既存の実ジャンプサーブ打点から3候補のうち
少なくとも1候補が有効になることを全得点、既存formation、左右チームで確認する。
1組でも全候補無効しか作れない場合は、ジャンプサーブ共通化へ着手せず停止する。

### SERVE-082-003: 政策甲と安全弁

政策甲と全候補無効は `IN_ACTION` だけを返す。
左右、上下入力を残さない。上昇中の `IN_JUMP` 保持だけは既存どおり許す。

サーブ打撃時の空中トスは `HitResolver._apply_hit()` で `serve_strike == true` となるため、
`opponent_return_vx()` と `-toss_fwd_vy` で相手コートへ返る。

同じ実ジャンプサーブ打点群で政策甲を実接触させ、全件がネットを越えて
相手コートへ落ちることを実装前診断で確認する。
1件でも失敗する場合は `hit_resolver.gd` や速度値を変更せず停止する。

### SERVE-082-004: 難易度境界

`_decide_serve()` の `P_TIQ >= 2` はジャンプサーブを行うかの発火条件なので残す。
選択関数へ入った後は、全難易度で同じ3候補と4政策を使う。

## 8. 120px制限撤去

### RANGE-082-001: 攻撃側

`_decide_air_hit()` の `can_spike` は `_attack_ok()` だけで決める。
ネットからの距離を条件にしない。

打撃可否は既存接触楕円、候補有効性、政策、安全弁が決める。
楕円を広げたり、新しい距離条件を加えたりしない。

炎必殺は既存どおり政策と試し打ちより先に確定するため、候補有効性を通らない。
120pxは通常攻撃と炎必殺が共有していた距離制限なので、その撤去により
既存の必殺専用条件を満たす深位置の炎必殺も解禁される。
これは距離制限撤去の直接効果として受け入れ、炎専用の代替距離や試し打ちを追加しない。
`_should_use_flame()`、入力、速度、ゲージ条件は変更しない。

### RANGE-082-002: ブロック側

`_decide_block()` から相手とネットの120px条件だけを除く。

次はすべて維持する。

- ブロック能力
- スタン条件
- 相手が空中
- ボールが相手の打点圏
- ネット際ポスト
- ラリーごとのブロッカー役
- 相方が会合可能かによる優先順位
- 歩行、ジャンプ、入力、物理

奥でトスした相手へ読み違えて反応する場合があることは、承認済みの駆け引きとして許す。

## 9. 状態と決定論

候補生成、格子評価、政策選択は状態を変更しない。

- 生の `rng` を消費しない
- `aitick` を進めない
- ボール、選手、タッチ、演出を変更しない
- 同じ同期状態、actor、入力候補、kから同じ結果を返す
- rollback後の再実行で入力と同期hashが一致する

状態変更は採用入力を `HitResolver` が実接触へ適用した時だけ行う。

## 10. テスト

### TEST-082-001: 幅格子

- k=0の論理格子座標列が中心1点で、正確速度と一致
- 非ゼロ `actual_vx` でk=1とk=3の論理格子座標数が5と13
- `actual_vx == 0` でk=1とk=3の論理格子座標数が3と7
- 歩幅0で速度が重複しても論理格子座標を削除しない
- 走査順が `iy` 外側、`ix` 内側
- 左右チームの速度集合と結果が鏡像
- `actual_vx == 0` では横点を除外
- kを上げても既存点が消えず、有効候補集合が縮まない
- 範囲外kは無効
- 非ゼロkで「格子は有効、中心実球はネット衝突、候補を実際に採用」が成立
- k=3の政策3は構造上3候補×13点以下
- `TRIAL_BAND_CURRENT_STEPS == 0`

### TEST-082-002: ジャンプサーブ

- 固定aitickで政策1、2、3、甲の入力が独立期待値と一致
- サーブとラリーが同じ3候補、探索順、有効判定を使う
- 政策甲と安全弁は方向キーなしの `IN_ACTION`
- 全候補有効fixtureでも政策甲は即時トスになり、早期return削除mutationで対象テストが赤
- 政策甲サーブは左右両チームで相手コートへ返る
- 政策甲サーブは4回目接触にならない
- 地上通常サーブの入力と既存結果が不変
- `P_TIQ` のジャンプ発火条件が不変
- 一つの接触窓で政策が変わらない
- 同じaitickの左右サーバーでactorによらず同じ政策になる
- 全得点、既存formation、左右チームの実打点で有効候補が1つ以上ある
- 同じ全組合せで政策甲の実球がネットを越えて相手コートへ落ちる

本番helperで期待値を再計算する自己一致だけにせず、入力ビット、相手側、候補数を独立に固定する。

### TEST-082-003: 深位置アタック

- ネットから120px超でも、楕円内かつ有効候補ありならアタック入力を返す
- 同じ深位置でも楕円外ならアタック入力を返さない
- 候補が全無効ならトスへ落ちる
- 深位置で炎必殺の既存専用条件が成立すれば、距離だけを理由に封じられない
- 炎必殺は試し打ちへ入らず、既存入力と速度を維持する

### TEST-082-004: 深位置ブロック

- 120px超の空中アタッカーと打点圏の球へブロッカーが反応する
- ネット到着後は既存のブロッカー役だけが跳ぶ
- 役持ち相方が会合不能なら代役が跳ぶ
- 能力なし、相手地上、球が打点圏外では反応しない
- 相手2人が同時に条件を満たしても、走査順変更で役割と優先結果が変わらない

### TEST-082-005: 決定論

- 同じ状態の再実行で候補、入力、同期hashが一致
- snapshot復元後の再実行で同じ入力と同期hashになる
- k=0機構追加だけでは既存ゴールデンが変わらない

## 11. #83性能ゲートの締め直し

### PERF-082-001: 恒久上限

#82完了後、承認済み #83設計どおり、既存の同じpolicy 2・3候補fixtureを
5つの独立プロセスで測定する。

```text
new_limit_ns = ceil(max(process_min_ns) * 1.20 / 1000) * 1000
```

計算値が65,000nsを超える場合は採用せず停止し、ユーザー承認を求める。

### PERF-082-002: 幾何診断

恒久fixtureとは別に、120px超の遠距離打点とジャンプサーブ打点を
一時プローブで各5独立プロセス測定する。

どちらかの最小値がPERF-082-001の新上限を超える場合は停止する。
fixture変更、上限緩和、恒久ゲート追加を自動採用せず、証拠をユーザーへ提示する。

両方が新上限以下なら、恒久テストは1件、`PERF_GATE` 1行、同じfixtureのまま
`AIR_UPPER_NS` だけを新値へ締める。

### PERF-082-003: 非ゼロk

k=3はproductionから到達不能なので専用性能上限を作らない。
非ゼロkをproductionへ配線する変更は #83の再設計と再測定を必須とする。

## 12. 固定値とコミット分離

変更理由を次の順に分ける。

1. 幅格子機構、production k=0
2. ジャンプサーブ共通化
3. 攻撃側120px撤去
4. ブロック側120px撤去と消滅テスト復活
5. #83上限締め直し

各段階で `run_tests.ps1` を実行する。

幅格子k=0で既存の固定値またはゴールデンが動いた場合は不具合として停止する。
挙動変更段でゴールデンが動いた場合は、その段だけを含む緑のツリーで
旧値、新値、変化checkpoint、次checkpointでの再合流有無、原因を記録してから更新する。

一つのゴールデン更新へ複数段の原因を混ぜない。

## 16. 停止条件

- 実ジャンプサーブ打点の1組でも3候補がすべて無効になる
- 政策甲サーブの1球でもネットを越えない、または相手コートへ落ちない
- サーブとラリーで候補、政策、有効判定が分岐する
- 120px撤去にブロック位置取り、役割、優先順位の変更が必要になる
- 非ゼロkの難易度値が必要になる
- k=3の構造上限39を超える

- 候補選択が状態を変更する
- 固定値変化に複数理由が混ざる、または原因不明

- 遠距離またはサーブ診断が新上限を超える
- 5回検証の1回でも性能または機能テストが赤になる
