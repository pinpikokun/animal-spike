## 設計の芯

原作CPU解析から得た最重要の知見:

> **原作CPUは「良い手を探す」のではなく「悪い手を弾く」設計。**
> 候補を乱数で作り、弾道シミュレータで棄却する。
> リメイク側が「最善手を評価する」方向で作ると、評価関数がレシーブに収束して
> アタックが出なくなる。
> **まず役割で攻撃を強制し、次に仮想打球テストで安全性を検証する。**

現行 `sim_cpu.gd` はまさに「最善手を評価する」構造で、ジャンプアタックが
多数の AND 条件の合流点に置かれている。どれか1つでも落ちると攻撃が消える。

### S1 の実体 (俺の初期診断を訂正)

**GDScript 4.6 では、三項式のオペランドになった配列リテラルは要素型を失う。
両辺とも純 int リテラルでも失敗する。** 最小再現で確認済み。

初版で「`best_delay == 999` の経路でのみ落ちる」「`p.x` が Variant だから」
と書いたのは**両方とも誤り**だった。条件に関係なく毎回落ちる。

`sim_state.gd:68` の既定プロファイルが `PRESET_MAX` (AB_SWEET 持ち) なので
**既定のCPU全員が該当**。フルスイートで SCRIPT ERROR が 10198行出ていた。

**修正は if/else に割ること。型付き一時変数では直らない。**

### S2 の実体 (不動点に収束する)

`desired_vx = dir * bump_fwd_speed` (40px/s、狙いなし) に入射慣性30%が加算される。
左右で打ち合うと写像 `a = 40 + 0.3b` の不動点 `40/(1-0.3) = 57.1 px/s`、
縦は `520/(1-0.3) = 742.9 px/s` に収束する。前進 約72px。

`toss_zone_front_px = 157` はネット(224)から67px。**前進72pxがこれを超えるため
ループが閉じる。** 慣性カットオフ (`inertia_min_speed` = 400px/s) は
不動点の入射 |v|≈723px/s が常に上回るため一度も発動せず、ループは自己修復しない。

### S4 の実体 (サーブ自爆の真因)

`sim_cpu.gd:371` は離陸tickにだけ `IN_JUMP` を返す。翌tickは `on_ground == 0` で
`:367` の分岐に入らず、打撃か歩行へ落ちる。**どちらにも IN_JUMP が無い。**
ラリー中の保持処理 (`:565-566`) は `:456-457` の PHASE_SERVE 早期returnで届かない。

可変ジャンプ (`player_movement.gd:169-170`) により本来135pxが**約18pxのホップ**に潰れる。
打点が低いと `toss_aim_vx` の除数が小さくなり、**横速度が爆発する** (実測 49px/tick)。

**触るべきはCPU入力であって物理定数ではない。**

### フェーズ3: CPU思考の原作アーキテクチャ化 (本丸)

#### 3-1. 役割のラリー単位確定

ラリー開始時にチームごとにアタッカー役を1名決める (決定論ハッシュ)。ラリー中は変えない。

- **アタッカー役だけがスパイクジャンプを打てる。** 相方はトスを上げる側に回る
- 前衛/後衛は相方との相対位置から導出し、一定間隔でスワップ
- ラリー単位の役割は `SimState` に持たせる
  (ロールバック対象。`to_int_array` / `load_int_array` / `state_hash` に必ず含める)

原作は9通りから抽選し、両方がアタッカーになる組み合わせを限っている。

#### 3-2. 仮想打球テストへの作り替え

空中で打つ直前に「その打ち方をしたらどこへ落ちるか」を実物理と同じ式で前方シミュレートし、
相手コートに入らない打ち方は選ばない。**どれも入らないならアタックを取り下げてトスに落とす。**

1. 候補を「スパイク3方向 → トス3方向」の順に並べる
2. 各候補について着弾点がネットを越え相手コート内に落ちることを検証
3. 検証を通った最初のスパイク候補を採る (**現行の「相手から最も遠い所」評価は撤去**)
4. スパイクが1つも通らなければトス候補へフォールバック
5. トスも通らなければ打たない

**評価を「最善手の探索」から「安全性の検証」へ変えるのがこの節の目的。**

#### 3-3. ジャンプ発火条件の絞り込み

原作は AND 3条件 + 高さ (横距離20px以内 / `|vx| < 5` / `|vy| < しきい値` / 十分高い)。
「良い球しか叩かない」条件を導入する。

### フェーズ5: 難易度段階の一本化 (ユーザー指示)

難易度段階 (`PRESET_WEAK` / `NORMAL` / `STRONG` / `MAX`) の作り分けを凍結し、
全CPUが同一の思考を使う。

- プロファイルのビットパック機構 (`P_AB`〜`P_TIQ`) は残す (将来の復活時に使う)
- 4つのプリセット定数は同一値を指すエイリアスにする (呼び出し側の変更を最小化)
- 難易度序列を検証していたテストは凍結し、凍結理由をテスト内に明記する

**原作も「敵CPUだけ GAME LEVEL を適用、味方CPUは常に最強」という配分だった**
(VB22.EXE 0xB54D)。ユーザー指示は原作の設計思想と一致している。

将来の難易度復活時は原作方式 (反応レイテンシ + 能力ゲート) を採る。
**狙いにノイズを注入する方式は採らない** (原作にその実装は存在しない)。

## 要判断 (ユーザーが決めること)

1. **レシーブの前方成分をどうするか。** 1-A (CPU側で閉じる) / 1-B (慣性を弱める) /
   1-C (原作回帰で前方成分を0に)。手触りの方向性の決定。
2. **入射慣性 (`hit_inertia_pct` 30%) は残すか。**
   解析で**原作にも慣性があった**ことが判明した (下入力レシーブ25%、ブロック100%)。
   **ユーザーの実機観察#15「慣性はある」が正しかった。**
   慣性の存在自体は原作準拠で、問題は値(30%)と、原作にはない前方定数40px/sとの合成。
3. **空中の上キーをアタックに戻すか。** 原作は「空中で上か下+ボタン = アタック」。
   現行は上をブロックに転用 (2026-07-20設計会)。
4. **ブロックの入力を原作の「前キー+ボタン」に戻すか。**
   原作は空中・地上ネット際の両方でブロックできる。現行は空中の上+ボタンのみ。
5. **「下ボタンでレシーブ構え」の仕様をどうするか。**
   現行は下+ボタン同時押し (`simulation.gd:258`) で仕様書どおり。
   ユーザーは「下ボタンを押しても」と言っている。
   **下単独で構え絵だけ出すと、ジャストレシーブ窓との視覚的区別が消えて
   「構えているのにジャストにならない」という別の混乱を生む。**
   操作の周知で済ませるか、仕様を変えるか。
6. **サーブ待ち中に構えを出すか。** 現行は PHASE_RALLY 限定。
   sim を触るとリプレイ・決定論・既存テストに波及する。
   表示層で入力を直接読むとロールバック再描画で状態が一致しない。
7. **空中から自陣へのつなぎ手段 (S7) を今入れるか。**
   仕様書は「事前には対策しない」と明記。フェーズ1〜2で3タッチが成立した後に
   プレイして判断するのが仕様書の意図に忠実。
   なお**原作には存在した** (空中トスは自陣狙い、敵陣送りは前キー時のみ)。
8. **配球ロジック (相手の薄いところを狙う) を持たせるか。**
   原作には存在しない。無くてもラリーは回る。優先度は低い。

## 触ってはいけないもの

- **sim層は int 固定小数のみ。float 禁止。** `test_no_float_in_sim.gd` が静的走査で守る
- 乱数は `_roll(SALT, s, idx)` の決定論ハッシュ。**キーに tick を直接使うな**
  (現行は `last_hit_tick` キーで「1タッチ内で判断がブレない」設計)
- CPU入力は `simulation.gd:111` → `_step_players_and_hits` を経て**無加工で**
  `PlayerMovement._step_player` に渡る。この経路に副作用を足すとロールバックが壊れる
- 憲法: CPUは相手チームの入力・照準を読まない。CPUの物理性能を強化しない
- 葉preload規律: 新コードは `simulation.gd` / `sim_cpu.gd` を preload しない
- モジュール境界: `ball_physics` / `player_movement` / `hit_resolver` / `sim_state`
- **sim層 ↔ 表示層の一方向依存。** 表示層が入力を直接読んで状態を作ると
  ロールバック再描画で不整合になる。フェーズ4は sim を一切触らずに完結させる
- `anim_select.gd` は純粋関数・テクスチャ非依存でヘッドレステスト可能。
  この性質を壊すな (`test_anim_select.gd` が依存)
- **キャラ見た目の正本は1つ** (char_id 単一辞書 + 完備性テスト)。
  アニメ名を増やすとき FALLBACK 辞書に入れ忘れると別キャラの絵で静かにフォールバックする
- **「物理は正直に、調整はパラメータで」**。
  `hit_resolver` に「ネット際だけレシーブが逆へ飛ぶ」ような条件分岐は原則違反。
  採るなら明示的に合意を取り直すこと
- ゴールデンハッシュ (`test_sync.gd` / `test_refactor_characterization.gd`) は
  挙動変更を含むコミットでのみ意図的に更新し、**なぜ変わったかを説明できること**。
  無説明の期待値更新は禁止

## 解析どうしの食い違いと、その決着

原作レシーブの実装箇所について2本の解析が対立したため、
ディレクターが状態ディスパッチ表を直接読んで決着させた。

```
7c37  cmp ax, 0xe
7c3a  jne 0x7c3f
7c3c  jmp 0x5bd0      ← state 0x0E → ハンドラ 0x5BD0
```

**打球物理担当が正しい。** state 0x0E (レシーブ構え) の専用ハンドラは `0x5BD0`。
検証担当の「`0x56C0 → 0x56D9` 経路」は誤り
(`0x56C0` は `0x5548` = state 2 / 0x0D = **地上打撃 (トス)** の中にある)。

参考: ディスパッチ表の主要な対応 (`0x7BC8`)

| state | ハンドラ | 意味 |
|---|---|---|
| 0, 0x63 | 0x4BD2 | 地上待機 / サーブ待ち |
| 1, 0x13 | 0x5136 | 空中 / ボール保持 |
| 2, 0x0D | 0x5548 | **地上打撃 (トス・サーブ打ち)** |
| 3, 0x0C, 0x11 | 0x5ECD | 空中打撃 / **ブロック** |
| 5, 6 | 0x6B6E | **横っ飛びレシーブ** |
| **0x0E** | **0x5BD0** | **レシーブ構え** |
| 7, 0x0F | 0x6F62 | 吹っ飛び |
| 9 | 0x72EA | ダウン |

### この決着が設計に与える意味

**原作のレシーブは目標x逆算を通らない。** 横速度はこう決まる:

```
vx = (ball_x - player_x) / 2 + rand%5 + 2*(右 - 左)     |vx| <= 4
```

**前方への定数バイアスが存在しない。** 方向は「体のどこでボールを捉えたか」で決まり、
そこに非対称な乱数 (`rand%5` = 0〜+4) が乗る。

対して現行は `vx = dir * 40px/s + 入射vx * 30%` で**常に前方**。
**この「常に前方」が、決定論的にネットを越え続ける無限ループの正体である。**

したがって:

- 「原作のレシーブは狙えない」という点では**現行と原作の方向性は一致している**
- 違いは**前方定数の有無**。原作は接触位置依存、現行は固定前進
- 1-C (`bump_fwd_speed` → 0) は原作準拠の方向だが、
  原作にある「接触オフセット項」がこちらには無いため、単に0にすると
  レシーブが真上に上がるだけになる (原作は左右に散る)
- **原作を本当に再現するなら `vx = (ball_x - p.x) / 2 + 決定論乱数` を入れることになる。**
  これは「どこで捉えたかで返る方向が変わる」という技術介入の余地を生む設計で、
  現行の「完全に制御不能」より面白くなる可能性がある。**ユーザー判断枠に追加。**
