# CPU空中打撃の予測式を実打球式へ合わせる設計

Status: 設計。ユーザー承認後に実装する。

基準HEAD: `68e8806`

対象タスク: #82 のうち、空中打撃候補の生成、試し打ち、政策選択、トスへの遷移。

## 1. 結論

直すべき主箇所は、`SimCpu._pick_air_shot()` の候補予測と
`HitResolver._apply_hit()` の実打球が別の式を使っている不一致であると確定する。

現行の予測は、狙った着地点から `HitResolver.toss_aim_vx()` で横速度を逆算する。
現行の実打球は、入力方向ごとの固定横速度
`spike_steep_vx`、`spike_mid_vx`、`spike_vx` を使う。
さらに実打球には、ジャスト、キャラクターの攻撃値、むらっけ、入射慣性、
制御喪失が反映される。予測はこれらの最終結果を使っていない。

したがって、予測側で別の近似式を調整してはならない。
実打球に入る最終 `(ball_vx, ball_vy)` を副作用なしで求める正本を一つ作り、
予測と実打球の両方がその正本を使う。

## 2. 実測結果の評価

### 2.1 根因判定に使える部分

最強CPUでは `P_TIQ == 3` なので、`_attack_ok()` は常に真である。
ネットから120px以内で `_pick_air_shot()` がトスを返した792観測は、
少なくともその観測時点ではアタック3候補が採用されなかったことを示す。

その792観測すべてで、現行予測の③奥が `_clears_net()` を通らなかった。
一方、実装上の③奥は3方向で最大の固定横速度と最も浅い縦角度を使う。
予測上の③奥は、その実速度ではなく着地点逆算値を使っている。

このコード差と実測は、偽陰性が候補予測の物理から発生していることを示す。
「ネットより高い打点が多い」という事実だけを根拠にはしない。
打点の高さだけでは、入射慣性を含む最終速度を確定できないためである。

### 2.2 測定の限界

`tests/zz_toss_cause.gd` は4人全員の `SimCpu.decide()` を毎tick呼ぶため、
一打を複数tick数える可能性がある。件数は実打撃回数として扱わない。
率も独立標本の比率ではなく、同じ接触窓の長さに重み付けされた観測率である。

また同スクリプトは、ネットから近いトスを無条件に
「3候補すべて無効」と分類しており、`_attack_ok()` と `ok[0..2]` を
分類条件として直接確認していない。この分類は強いCPUには混同の余地がある。

ただし最強CPUは `_attack_ok()` が常に真であり、現行 `_pick_air_shot()` は
有効なアタック候補を一つでも見つければトス候補よりアタックを優先する。
よって最強CPUの792観測は根因判定に使える。

修正効果の件数比較には、この使い捨て測定を合格条件として使わない。
実装検証では `last_hit_tick` または `last_touch_idx` の変化を境に、
実際に成立した一打を一回だけ数える。

## 6. 共通の実打球速度

### 6.1 新しい読み取り専用API

`src/sim/hit_resolver.gd` に次の静的関数を置く。

```gdscript
static func preview_air_spike_velocity(
		s, actor: int, cfg, input: int, d2: int) -> Vector2i
```

戻り値は、その状態で同じactorが同じinputとd2で通常の空中アタックを成立させたとき、
実際に `s.ball_vx` と `s.ball_vy` へ入る最終速度である。

関数は状態を一切変更しない。次を現行 `_apply_hit()` と同じ順序で読む。

1. チーム方向と横入力
2. サーブ打撃か
3. 特殊技か
4. d2によるジャスト成立
5. バーンアウトによるジャスト無効
6. 入射速度が慣性しきい値を超えるか
7. キャラクターの受け流し
8. サーブ打撃の慣性ゼロ
9. 相手のパワー球による制御喪失
10. 通常またはジャストの速度倍率
11. キャラクターの攻撃値
12. むらっけ倍率
13. 3方向の固定 `(vx, vy)`
14. `aim_pct` と入射慣性

CPU候補は必殺技入力を渡さないが、APIは実打球側の正本であるため、
入力の解釈自体は `_apply_hit()` と一致させる。

### 6.2 実打球側の利用

`HitResolver._apply_hit()` は `INTENT_AIR_SPIKE` の速度を独自に再計算せず、
打撃処理による状態変更を始める前の状態から
`preview_air_spike_velocity()` を一度呼び、その戻り値を保持する。

演出、ゲージ消費、パワーボール、ノックバック、ガード値などの既存処理は維持する。
速度を代入する箇所だけが保持済みの戻り値を使う。

これにより、予測と実打球が同じ補助関数を使うだけでなく、
実打球の速度そのものがその補助関数の結果になる。

### 6.3 CPU側の利用

`SimCpu._pick_air_shot()` は `toss_aim_vx()` と `spike_target_x()` を
アタック候補生成に使わない。

3候補それぞれについて実際に返す入力ビットを作り、
同じ `d2` とともに `preview_air_spike_velocity()` へ渡す。

```text
①手前 = ACTION | DOWN | ネット逆方向
②中央 = ACTION | DOWN
③奥   = ACTION | DOWN | ネット方向
```

得た最終速度を `_land_x_from()` とネット通過判定へ渡す。
CPU側で固定速度、倍率、慣性、キャラクター補正を再実装してはならない。

## 7. 候補の有効判定

### 7.1 通常

候補は次の両方を満たすときだけ有効である。

1. 最終落下xが相手コート側にある
2. 打点が自陣側なら、ボール中心がネット面を通過するとき
   `ball_radius` を含めてネット上端を越える

落下点は壁反射を含む現行 `_land_x_from(..., max_bounce = 3)` を使う。

### 7.2 既にネットを越えている球

打撃開始時にボール中心が打ち手から見て相手コート側にある場合、
ネット通過は既に完了している。`_clears_net()` に再通過を要求してはならない。

この場合も落下点が相手コート側にあることは検査する。
接触可否は現行の打撃楕円と `HitResolver._resolve_hit()` に従う。
ネットを越えていても楕円内ならCPUは打撃入力を出す。

## 8. 4政策

### 8.1 確率

政策は次の固定比率とする。

| 政策 | 確率 | 探索 |
|---|---:|---|
| 政策1 | 30% | ①、②、③の順で最初の有効候補 |
| 政策2 | 30% | ③だけを試し、有効なら採用 |
| 政策3 | 30% | ①、②、③の全有効候補から相手2人に最も遠い候補 |
| 政策甲 | 10% | 試し打ちをせず最初からトス |

ユーザー確定の「10%は甲」を、既存の「最初からトス」政策へ対応させる。
政策1から3で対象候補が無効なら、安全弁トスへ移る。

### 8.2 抽選

本作独自抽選なので、生の `rng` を消費しない。
`sim_cpu.gd` の予約済み用途IDを再利用せず、次を追加する。

```gdscript
const SALT_AIR_SHOT := 8
```

抽選値は次で求める。

```gdscript
var roll: int = SimRng.derived_value(s.aitick, 0, SALT_AIR_SHOT) % 10
```

写像は固定する。

- 0..2: 政策1
- 3..5: 政策2
- 6..8: 政策3
- 9: 政策甲

actor項は0固定とする。全員が同じ打球系列で同じ政策を見る。
`aitick` は実打球まで変化しないため、同じ接触窓で政策は変化しない。
同じ政策を毎tick純粋に再導出してよく、状態へ保存しない。

### 8.3 政策3の評価

着地点から各相手までの横距離を求め、近い側の距離を候補得点とする。
スタン加点を含む現行 `_pick_air_shot()` の得点式を維持する。

最大得点が同じなら①、②、③の走査順で先に見つかった候補を採用する。

## 9. 難易度

#82の候補生成、有効判定、4政策、確率、探索順、得点式には
CPUプロファイルによる分岐を作らない。全難易度で最強基準の正確な最終速度を使う。

`P_TIQ >= 2` のときだけ `_pick_air_shot()` を通す現行分岐は撤去する。
空中打撃選択へ到達したCPUは同じ選択関数を通る。

既存の `AB_ATTACK` と `_attack_ok()` は、この選択へ入る前の攻撃能力と許可である。
本設計ではその値を変更しない。ここを通過した後には難易度差を作らない。
弱いCPUへ新たに攻撃能力を付与することは本設計の対象外である。

## 10. トスの行き先

政策甲と政策1から3の安全弁は、同じトス処理を使う。
入力は左右と上下を消した `IN_ACTION` とする。
上昇中の `IN_JUMP` 保持は移動物理用なので残してよい。

原作準拠で、打撃前の自チームタッチ数によって行き先を分ける。

- 1打目または2打目: 自陣前方へ上げる
- 3打目: 相手コートへ返す

判定式を次に固定する。

```gdscript
var touches_after: int = s.touches + 1 if s.last_touch_team == team else 1
var returns_to_opponent: bool = touches_after >= cfg.max_touches
```

1打目または2打目の空中トスは、現行の自陣前方正本
`toss_target_x(team, 0, cfg)` と `toss_aim_vx()` を使う。
これはネットから自陣側40pxの原作前方目標に対応する。

3打目は地上と同じ強制返球規則を空中にも適用し、
現行 `opponent_return_vx()` と `-cfg.toss_fwd_vy` を使う。
この返球は相手コートへ入る既存保証を維持する。

トス上手、トス下手、むらっけなど既存の特性契約は変更しない。
本設計によって新しいトス性能差を追加しない。

## 11. 発火条件と状態遷移

空中接触楕円へ入ったときの優先順位は次とする。

1. 既存の必殺技条件が成立すれば必殺技
2. 通常アタックが許可されていれば4政策を決定
3. 政策1から3は指定候補を実打球速度で試す
4. 有効候補があればその入力を返す
5. 政策甲または有効候補なしならトス入力を返す
6. `HitResolver` が実接触を一度だけ成立させ、`aitick` を進める

試し打ちでは次を変更しない。

- `ball_x`, `ball_y`, `ball_vx`, `ball_vy`
- プレイヤー全フィールド
- `rng`, `aitick`
- タッチ数、最終接触者
- 演出、ゲージ、攻撃種別

## 12. ジャンプ #85

#85は本設計より先に直さない。

理由は、#85が「どの球へ跳ぶか」という空中接触前の発火条件を変えるのに対し、
今回確定した不具合は、既に接触圏へ入った後に候補を別物理で無効化するものだからである。
最強CPUのトス1112観測のうち、ネット上端より低い打点は24観測だけであり、
今回の主症状を低いジャンプ打点だけでは説明できない。

#85を先に入れると接触標本そのものが変わり、予測式修正の前後比較が濁る。
したがって、まず本設計を実装して候補予測と実打球を一致させる。
その後、修正済みの基準上で#85を独立設計、独立検証する。

#85では `PlayerMovement`、`_jump_will_meet()`、`_sweet_jump_plan()`、
ジャンプ発火のAND条件を扱う。本設計ではこれらを変更しない。

## 14. 検証方法

### 14.1 速度の正本

次の組み合わせで `preview_air_spike_velocity()` の値を
独立した固定期待値と比較する。

- 左右チーム
- ①、②、③
- 通常、ジャスト
- 入射速度なし、上昇球、下降球
- 通常打撃、サーブ打撃
- 標準キャラ、攻撃値差、むらっけ
- 通常球、制御喪失対象のパワー球

固定期待値は既存の設定値と契約式からテスト側で明示する。
本番の共通APIを呼んで期待値を再計算してはならない。

同じ組み合わせで `_apply_hit()` 後の実 `ball_vx/ball_vy` が
共通APIの戻り値と一致することも検査する。
独立期待値検査と一致検査の両方を置き、自己一致だけにしない。

### 14.2 根因の回帰

現行の着地点逆算候補では③奥がネット判定に落ち、
同じ状態の実打球速度ではネットを越える固定フィクスチャを一つ置く。

修正後は次を同時に満たすこと。

- ③奥が有効
- 政策2で③奥を採用
- 実際に `_apply_hit()` した球がネットを越える
- 予測落下側と実打球側が同じ相手コート側に落ちる

### 14.3 政策

0から9の各剰余を作る `aitick` の固定ベクトルを用意し、
3 / 3 / 3 / 1の写像を直接検査する。

- 政策1は最初の有効候補で停止
- 政策2は③だけを一回評価
- 政策3は3候補を評価し最遠を選ぶ
- 政策甲は候補評価ゼロ回
- 政策1から3は全候補無効時にトス

同じ `aitick` でactor、tick、難易度プロファイルだけを変えても、
選択関数へ入った後の政策と候補結果が変わらないことを検査する。

### 14.4 トス

- 1打目の空中トスが自陣前方へ向かう
- 2打目の空中トスが自陣前方へ向かう
- 3打目の空中トスが相手コートへ向かう
- 左右チームで鏡像になる
- 政策甲と安全弁が同じトス入力になる
- 3打目が4回目接触にならず、相手コートへ返る

### 14.5 ネット越し接触

ボール中心をネットの相手側、CPUを自陣側、両者を接触楕円内に置く。
CPUが `IN_ACTION` を返し、候補が「ネットを再通過しない」ことだけを理由に
無効にならず、`HitResolver._resolve_hit()` で接触が成立することを検査する。

楕円外の対照ケースでは打撃入力または接触が成立しないことも検査する。

### 14.6 決定論と全件

実装担当は正規入口だけを使う。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File run_tests.ps1
```

同じ初期状態、入力列、シードの再実行で同期ハッシュが一致すること。
ゴールデン値が変わる場合、他の全検査が緑になった後、
今回の入力選択変更だけが原因だと実差分で確認してから更新する。

## 15. 合格条件

次をすべて満たしたときだけ合格とする。

1. CPU予測と実打球が同じ最終速度APIを使う
2. CPU候補生成から `toss_aim_vx()` と `spike_target_x()` が消える
3. 実空中アタックの3方向速度設定値が変わらない
4. 根因回帰フィクスチャで偽陰性が消える
5. 4政策が30% / 30% / 30% / 10%
6. 10%の政策甲が試し打ちなしのトス
7. 選択処理に難易度分岐がない
8. 1打目と2打目の空中トスが自陣前方
9. 3打目の空中トスが相手コートへ返る
10. 既にネットを越えた球も楕円内なら接触できる
11. #85のジャンプ発火コードに差分がない
12. 正規入口の全テストが緑
