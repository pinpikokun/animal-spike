# スパイクの速度を固定にする (落下点からの逆算をやめる)

Status: 設計。実装未着手 (2026-07-26)。

## 1. 対象

**空中アタック(スパイク)の速度。** アタックサーブも同じ処理を通るため含まれる。

**対象外**: 地上トス、3打目の返球、サーブのトス、ブロック、必殺技。
返球は `2026-07-26-return-over-net-design.md` が扱う。

## 2. 解く問題

**同じ入力でも、立つ位置でスパイクの速さが 2.3 倍変わる。**

実測 (2026-07-26、`tests/zz_spike_speed.gd`。使い捨てのためコミットしていない)。
左チームが空中で下+ボタンを押したときの横速度 (px/秒)。

| 打点(ネットから) | 高さ80で打つ | 高さ140で打つ |
|---|---|---|
| 270 | **1578** | 1052 |
| 220 | 1391 | 927 |
| 170 | 1203 | 802 |
| 120 | 1016 | 677 |
| 70 | 828 | 552 |
| 30 | **678** | 452 |

**コート奥から打つとネット際の 2.3 倍速い。**

### 2.1 何が起きているか

`hit_resolver.gd` のスパイクは、**狙う場所を決めてから、そこへ届く横速度を逆算している。**

```gdscript
svx = toss_aim_vx(打点, 縦速度, spike_target_x(...), cfg)
```

遠くから同じ場所を狙えば速くなる。**位置で速度が変わるのは、この作りの副作用。**
「そうしよう」と決めた記録はどこにも無い。

### 2.2 遊びとして何が悪いか

- **なぜ今の一撃が弱かったのか、遊ぶ側に説明できない**
- **ネット際のスパイクが一番遅い。** バレーで一番決まる場所が一番弱い球になる
- 設定ファイルの `spike_vx_px_s`(680) が**ほとんど効いていない。**
  その値がそのまま出るのは「ネット際・高さ80」の一点だけ

なお**ダメージ自体は速度で変わらない**(キャラのランクごとの固定値)。
変わるのは相手が反応できるかどうか。

### 2.3 サーブが入らない件の原因でもある

コートを 448 → 576 へ広げたことで、**コート奥から打つスパイクが以前より速く・平らになった。**
アタックサーブは壁際から打つため、この最も速く平らな球になる。
**ネットに着く頃の高さが足りず、ネットに当たる**(2026-07-26 実測)。

**打点を上げるだけでは症状が隠れるだけ。根はここにある。**

## 3. 原作はどうしているか (逆アセンブルで確認、2026-07-26)

`0x6115` 空中アタック打球式、3方向。**すべて固定値。打点の位置を一切見ていない。**

```
6156  mov ax, 6            ; 既定
615d  mov [ball_vx], ax
6160  mov [ball_vy], 0xc   ; 12

6166  cmp [逆方向キー], 0   ; 押していれば
617a  mov [ball_vx], 4×向き
617d  mov [ball_vy], 0x10  ; 16

6186  cmp [ネット方向キー], 0 ; 押していれば
6199  mov [ball_vx], 7×向き
619c  mov [ball_vy], 4
```

| 入力 | 横速度 | 縦速度 | 性質 |
|---|---|---|---|
| 逆方向(手前を狙う) | **4** | **16** | 遅くて急。ネット際に鋭く落ちる |
| なし(中央) | **6** | **12** | 中間 |
| ネット方向(奥を狙う) | **7** | **4** | 速くて浅い。奥まで伸びる |

**打ち分けは「速度と角度の組」で表現されている。落下点は結果。**

**中央の 6 は 4 と 7 の平均(5.5)ではない。3つとも独立した値。**

## 4. 採用する設計 (2026-07-26 ユーザー決定)

> だれも必ず狙った場所に落とす必要があるなんて言ってないんじゃない？
> 狙った場所に届かなかったらそれはただ打つ高さが低かっただけでしょ。
> つまり速度を早くする必要がない。

### 4.1 横速度も固定値にする

**逆算をやめ、3方向それぞれに固定の横速度を持たせる。**
縦速度は既に3方向の固定値になっているので、**横を同じ形に揃えるだけ。**

**落下点は結果として決まる。届かなければ打点が低かったということ。**
これはプレイヤーの技術であり、上達の余地になる。

### 4.2 「必ず入る」保証はスパイクには付けない

| | 必ず入る保証 |
|---|---|
| 3打目の返球・サーブ | **要る。** ルール上返さないと失点する |
| **スパイク** | **要らない。** 打つかどうかはプレイヤーの選択 |

役割が違う。返球の保証(別設計書)はそのまま残す。

### 4.3 値 (比率は原作、絶対値は実プレイで決める)

**速度そのものは原作から換算できない**(原作のフレームレートが不明)。
**比率は比較できる**ので、比率を原作から取る。

原作の横速度の比 **4 : 6 : 7**。

奥狙いを既存の `spike_vx_px_s`(680) に合わせて比率を掛けた初期値:

| 狙い | 横速度(px/秒) | 縦速度(px/秒) | 出典 |
|---|---|---|---|
| 手前(逆方向) | **389** | 440 | 横は原作比 4/7 × 680。縦は既存 `spike_steep_vy_px_s` |
| 中央(なし) | **583** | 350 | 横は原作比 6/7 × 680。縦は既存2値の中間 |
| 奥(ネット方向) | **680** | 260 | 横は既存 `spike_vx_px_s`。縦は既存 `spike_vy_px_s` |

**横の3つは独立した設定キーにする。** 原作が独立した3値を持っているため。
中央を平均として計算で作らないこと。

**既存の `spike_vx_px_s`(680) と `spike_steep_vx_px_s`(460) は「遊んで決めた値」ではない。**
横速度が逆算されていたため、これらは特定の一点でしか効いていなかった。
**守るべき手触りは存在しない**ので、比率を優先して 460 → 389 に変える。

**縦速度は変えない。** 3方向とも既に原作と同じ形(手前が急、奥が浅い)になっている。

**絶対値は実プレイで調整する。** 比率だけが原作由来で、スケールは遊んで決める。

### 4.4 むらっけ・入射慣性は残す

現行の `aim_pct`(むらっけ)と入射慣性はスパイクに掛かっている。
本作独自の機構であり、**今回は触らない。**

## 5. CPU への影響 (重要)

**固定速度にすると、CPU は「この打ち方で相手コートに入るか」を自分で判断する必要が出る。**

現在は逆算のおかげで必ず狙った場所に落ちるため、CPU は判断しなくてよかった。
固定速度では**位置によっては入らない**ので、入らない打ち方を選ぶと自滅する。

**原作はこれを「打つ前に試す」で解決している。** 残タスク #82。

```
0x9471  試行1: vx=3, vy=0x12 で試す
0x94F2  試行2: vx=5, vy=0x0E で試す
        → 相手コートに入る打ち方を選ぶ
```

**#82 は独立したタスクではなく、この設計の片割れ。** 本設計と組で入れないと
CPU が自滅する。**着手時に必ず一緒に扱うこと。**

## 7. やってはいけないこと

- **落下点を決めて速度を逆算する形に戻さないこと。** それが本設計が消す対象
- **スパイクに「必ず入る」保証を付けないこと**(4.2)
- 縦速度の3方向の値を変えないこと。原作と同じ形になっている
- 地上トス・返球・ブロック・必殺技の速度計算に手を出さないこと
- **比率以外を原作から持ってこないこと。** 速度の絶対値は換算不能

## 8. 検証方法

1. **同じ入力なら、打点の位置によらず横速度が同じ**であることを検査する。
   本設計の核心。2節の 2.3 倍が 1.0 倍になること
2. 3方向で速度と角度が意図どおり分かれること(手前=遅く急 / 奥=速く浅い)
3. 同じ状況で必ず同じ結果になること(決定論)
4. **CPU が自滅していないこと。** #82 が入るまでは失点が増えうる。
   入る前に計測して、悪化幅を把握しておくこと
5. 実プレイでユーザーが手触りを判断する

## 9. 経緯

2026-07-26、コート拡張後に CPU のアタックサーブがネットに当たる問題を追う過程で発覚した。

Claude Code は当初「打点が低いのが原因」と考え、打点を上げる案を検討していた。
ユーザーの指摘により、**速度が位置で変わること自体が異常であり、
サーブが入らない原因の一つである**ことが分かった。

さらに Claude Code は「狙った場所に必ず落とすには逆算するしかない」と説明したが、
**「必ず落とす」は誰も要求していなかった。** 仕様書にあるのは狙いの方向だけで、
必達要件は Claude Code の思い込みだった。ユーザーの指摘で判明した。
